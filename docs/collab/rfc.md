# RFC: совместное редактирование DeckCraft (PPTX)

- Статус: Draft (на ревью `craft/reviewer`)
- Автор: `deckcraft/envoy`
- ADR: `bus/decisions/0001-op-unit.md` … `0010-undo-offline.md`,
  свод: `.craft/protocol/ARCHITECTURE.md`
- Upstream issue/PR: не открывались (по house rules PR не упоминает авторство
  агента; issue — после ревью RFC)
- Факты: `upstream/docs/collab/study.md` (коммит `159ed07e`),
  `upstream/docs/collab/options.md` (коммит `3d5b945d`)

## 1. Контекст

DeckCraft — презентационный редактор на Rust/egui, `.pptx`/`.potx`/`.ppsx`,
202k строк, 24 крейта, 329 команд, 2432 теста. Сейчас в нём **нет** совместной
работы: один документ, один пользователь, сетевого кода нет ни одного
(`study.md` §7).

Что есть и на что опирается этот RFC:

- **Одна точка мутации.** Любое действие — `CommandSpec` с JSON-параметрами,
  исполняется через `Session::execute` (`engine/src/lib.rs:636`); UI, CLI,
  control-канал и MCP идут через неё (`study.md` §3).
- **Мутация copy-on-write.** `Session::edit` клонирует `Vec<Arc<Slide>>` и
  делает `Arc::make_mut` только на затронутом слайде (`:727`).
- **Производное состояние считается кодом**: рамка группы и `child`-пространство
  (`cmd/arrange.rs:238-315`), маршрут коннектора (`connect::reroute`), autofit
  текста. Пересылать его нельзя (`study.md` §6).
- **Undo — снимки `Arc<Presentation>`** на команду, 500 шагов / 256 MiB
  (`engine/src/lib.rs:167,258,825`).
- **Нативный формат** `.deckcraft` = zip с `presentation.json` (модель **без**
  байтов медиа) + `media/<id>` + `chart-parts/<index>`
  (`crates/format/src/lib.rs:1-5,73-100`) — готовый формат снапшота.
- **Запись `.pptx`**: `deckcraft_pptx::export_as(p, "pptx")`; writer
  перенумеровывает `p:sldId@id = 256 + i` (`pptx/src/write.rs:1112`) и `cNvPr`
  по части (`write/shapes.rs:20-40`).

Чего нет и что добавляет этот RFC: транспорт, сервер, операции, presence,
per-user undo, commit, feature flag, тесты сходимости.

Решения приняты в ADR 0001–0010; RFC их не пересматривает, а раскладывает на
DeckCraft.

## 2. Цели и не-цели

**Цели (из `TASK.md` §1–8).**

1. 2–5 участников одновременно правят одну презентацию; результат — один
   `.pptx`.
2. Слайды, фигуры, текст, таблицы, z-order, группы, анимации, переходы,
   заметки и комментарии сходятся без потерь.
3. Presence: активный слайд, выделение, каретка, viewport.
4. Роли `owner`/`editor`/`viewer`, проверка на сервере; viewer не пишет.
5. Per-user undo: отмена не откатывает чужие правки.
6. Reconnect и догон; идемпотентность; никакого полного документа на нажатие.
7. Commit отдаёт `.pptx` кабинету; внешнее изменение → `409`.
8. Одиночный режим — по умолчанию и без изменений; фича за флагом.

**Не-цели (v1).**

- Аккаунты, облако, команды, шаринг ссылками.
- Совместный показ слайдов и presenter view как отдельная фича (показ остаётся
  локальным; правки во время показа не блокируются, но не синхронизируют
  позицию показа).
- Офлайн-редактирование: только reconnect/догон (ADR-0010).
- CRDT/OT как механизм сходимости (ADR-0001).
- Макросы `.pptm`, legacy `.ppt`, SVG-рендер, ODP: вне области и сейчас.
- Изменение CI в feature-PR (house rules).

## 3. Модель данных для синхронизации

### 3.1 Документ на сервере

`Document = base snapshot + tail journal + keys map + tombstones + media store`.

- **База** — нативный `.deckcraft`: `presentation.json` (модель целиком, включая
  `Opaque`, `raw_ext`, `kept_parts`, `tags`, `Chart.kept`) + бинарные
  `media/<MediaId>` и `chart-parts/<index>`. Отдельного opaque-блоба не нужно:
  непромоделированное **уже** сериализуется в модели (`ShapeKind::Opaque{xml,
  preview, parts}`, `raw_ext`, `Presentation.kept_parts`), в отличие от WordCraft
  с `#[serde(skip)]` (`study.md` §5). Медиа вынесены из JSON — значит база и
  медиа-хранилище разделимы.
- **Хвост журнала** — записи `{version, opId, actorId, kind, target, payload,
  result, ts}`; обрезается по версии базы (ADR-0005).
- **Карта ключей** `slideKey ↔ SlideId`, `shapeKey ↔ ShapeId`, `MediaId ↔ sha256`
  — часть метаданных снапшота, в `.pptx` не пишется (ADR-0002).
- **Надгробия** `deletedSlide/deletedShape/deletedMedia`; TTL ≥ окна дедупа
  (24 ч) и ≥ максимального разрыва, который прощает reconnect.

### 3.2 Единица операции (ADR-0001)

Операция — нормализованная команда с явным адресом; сервер исполняет её и
возвращает авторитетный результат.

```json
C→S {"type":"op","opId":"<uuid>","doc":"<fileId>","baseVersion":41,
     "kind":"command|structural",
     "target":{"slide":"<slideKey>",
               "shape":"<shapeKey>",
               "text":{"cell":[r,c],"anchor":[p,ch],"caret":[p,ch]}},
     "payload":{"cmd":"shape.move","args":{"x":120.0,"y":64.0}}}
S→C {"type":"applied","opId":"<uuid>","version":42,
     "result":{"command":{"cmd":"shape.move","target":{...},"args":{...}},
               "delta":{"changes":[{"slide":"<slideKey>","shape":"<shapeKey>",
                                    "fields":["xfrm"]}]}}}
```

Правила нормализации (обязательны, иначе операция нереплицируема):

- **Никаких UI-команд на проводе** (ADR-0001 §2). `text.insert` сегодня берёт
  каретку из `selection.text` (`cmd/text/editing.rs:75-100`), `shape.move` —
  выделение (`cmd/shape.rs:61-66`), `format.bold` действует «на текст или
  фигуры» (`cmd/format.rs:43`). На провод едет `target` с явным адресом и
  `args` с итоговыми значениями.
- **Относительные значения запрещены**: `shape.move {dx,dy}` переводится в
  абсолютные `{x,y}`; `text.insert` — в `{pos, text, props}`;
  `arrange.*` — в итоговый порядок или `structural`.
- **`context`** (общий конверт ARCHITECTURE §2.2) у DeckCraft несёт только
  значения: `slideKey`, `targets[]`, `text`-позиции. Предпочтения
  (`Session.prefs`: smart quotes, `mac_keys`) в операцию не входят; клиент
  нормализует текст до отправки (`cmd/text/editing.rs:60-72`).
- **`preview`** — необязательный локальный id: клиент применяет команду
  оптимистично и при `applied` заменяет результат авторитетным.

`format_set` покрывает `format.bold/italic/underline/strikethrough/superscript/subscript/font/size/color/highlight/alignLeft/alignCenter/alignRight/justify/caps/spacing/clear`. Перечисление `FormatCmd` (а не строка) закрывает allowlist на уровне типа; `FormatCmd::accepts` не даёт положить в `args` чужой ключ. Множество фигур для `format.*` нормализуется в **N операций по одной фигуре** (решение по §13 п. 3): так undo остаётся объектным, а `applied` несёт понятный адрес. Внутри одной фигуры операция несёт **список адресов** `addresses`: для не-таблицы это ровно один адрес (её собственное тело), для таблицы — один адрес на ячейку. Ячейка таблицы — отдельный адрес `cell: [row, col]`, он берётся из аргументов команды, из выделенных ячеек или из каретки/диапазона внутри ячейки, а применяется к телу **этой** ячейки (не к пустому `text` таблицы). Выделение нескольких ячеек — это **одна операция с N адресами, по одному на ячейку**, а не один адрес, расширенный до таблицы: сервер форматирует ровно перечисленные ячейки, а undo возвращает тела ровно этих ячеек одним `cells_text` (`shape.setCellBodies`, по `shape.setField {field: cellText}` на ячейку в одном шаге). Пустой список адресов, ячейка дважды, несуществующая ячейка, диапазон или каретка за концом тела, таблица без адреса ячейки и несколько адресов у не-таблицы отклоняются до первой записи; соседняя ячейка, которой нет в списке, не меняется никогда.

Диапазон **ранов** внутри тела — адрес `range: {from, to}`, смещения в символах по всему телу (перевод абзаца — один символ), те же координаты, что у `text.insert`/`text.delete`. На проводе именно смещения, а не индексы ранов: правка текста на другой реплике расщепляет и сливает раны, поэтому индекс рана недетерминирован, а смещение — детерминированно. Клиент берёт диапазон из текстового выделения (в теле фигуры или в одной ячейке); каретка без выделения — тоже адрес (`caret: offset`), но только в собственном теле фигуры, а каретка в ячейке таблицы по-прежнему адресует всю ячейку. Каретка не расширяется до слова на клиенте: сервер ставит то же свёрнутое выделение на то же авторитетное тело и прогоняет одиночную `format.*`, поэтому команда ранов сама расширяет каретку до слова, в котором та стоит (как в обычном редакторе), команда абзаца берёт абзац, а каретка на границе слова задаёт форматирование для следующего ввода, не трогая существующие символы — и обе реплики получают один результат. Каждая реплика переводит два смещения (или каретку) в `(абзац, символ)` одной и той же функцией (`offset_position`), поэтому набор форматируемых ранов — детерминированная функция авторитетного тела. Сервер перебазирует адреса по журналу (§4.4): вставка до диапазона двигает оба смещения (и каретку), удаление внутри сжимает диапазон, удаление всего диапазона делает адрес пустым — операция отклоняется `invalid` до первой записи, а не форматирует другие символы; строка/столбец таблицы двигает адрес каждой ячейки, а удаление строки/столбца с любой адресованной ячейкой отправляет операцию в `stale`. Адаптер резолвит тела и проверяет каждый адрес (`position_offset(offset_position(x)) == x`) до первой записи; выделение получателя возвращается на место, потому что формат не двигает текст.

Остаток табличной поверхности — стиль, опции стиля, заливка ячеек, merge/split и размеры столбцов и строк — идёт теми же итоговыми значениями: `table_style` несёт имя стиля, `table_options` — все шесть независимых булевых опций стиля (клиент применяет названные пользователем флаги к таблице, которую видит, и отправляет весь набор итоговых значений: частичный набор зависел бы от того, чья устаревшая копия пришла первой), `table_cell_fill` — одно значение заливки и **явный** список ячеек (нормализованный из выделения отправителя, поэтому выделение получателя ничего не решает; `inherit` снимает явную заливку, `none` ставит пустую, `solid` — один цвет), `table_merge`/`table_split` — итоговые углы и анкор, `table_column_width`/`table_row_height` — итоговые числа (клиент клампит их теми же границами, что одиночная команда). Каждая из них — одна команда движка (`table.style`/`table.options`/`table.cellFill`/`table.merge`/`table.split`/`table.columnWidth`/`table.rowHeight`) на авторитетном состоянии, поэтому все реплики получают одинаковый результат; адрес — таблица (`target.slide` + `target.shape`), а не отдельная ячейка. Merge и split не двигают индексы ячеек, поэтому класс — command: отложенная операция по ячейке перебазируется только строкой/столбцом (`table_edit`) и отклоняется `stale`, если merge накрыл её адрес (её текст теперь в анкоре слияния, писать в неё нельзя). Образ шага undo — **вся таблица** (`shape_field{field: table}`), как у `table.edit`: стиль, опции стиля, заливка, слияние и размер меняют таблицу, не называя ячейку, которую можно было бы восстановить отдельно, а команды `table.*` не выражают прежнее значение целиком (заливка ячейки — это `Option<Fill>`, а не только `solid`/`none`). Поэтому чужая правка той же таблицы после шага даёт `undo-conflict`, а undo возвращает таблицу точно, вместе с её боксом (движковая `shape.setField{field: table}` синхронизирует ширину и высоту фигуры с таблицей).

SmartArt идёт тем же правилом одного итогового значения: `smart_art_set` несёт **весь** `Diagram` — layout, контур (текст, уровни, assistant, title, picture), style и colors. Команды `smartArt.setNodes` (в формах `nodes`/`lines`/`index`+`text`/`title`), `addNode`, `removeNode`, `promote`, `demote`, `layout`, `style` и `colors` нормализуются на клиенте через движковый `smartArt::plan` — ту же функцию, которой пользуется одиночная команда, — поэтому отправляется ровно то значение, которое она оставила бы: смена layout сбрасывает сохранённый в файле layout, смена style/colors — свои XML, добавление и удаление узлов меняет список. Значение считается от **своего** состояния отправителя (с синхронизированным из фигур текстом, как перед каждой регенерацией), поэтому импортированный рисунок и чужая устаревшая копия ничего не решают. Адаптер прогоняет `smartArt.setDiagram`: команда десериализует значение, проверяет layout/style/colors, размер и число узлов и регенерирует дочерние фигуры группы из итогового значения, поэтому все реплики получают одинаковый рисунок. Образ undo — **вся группа** (`shape_field{field: smartArt}`, модель `Shape` в JSON: diagram и сгенерированные дети с их id): правка контура регенерирует детей с новыми id и заменяет drawing импортированного файла, поэтому одно значение diagram шаг не восстанавливает, а чужая правка той же группы после шага даёт `undo-conflict`. Вставка идёт тем же правилом: `insert.smartArt` несёт **весь** `Diagram`, который оставила бы одиночная команда (нормализатор считает его движковым `smartart::insert_plan`: layout, контур, значения по умолчанию), плюс необязательный итоговый бокс; движок проверяет layout/style/colors, число узлов, текст и размер до первой записи и регенерирует детей, поэтому все реплики получают одинаковый рисунок, а враждебное дерево не добавляет фигуру и не двигает version. Образ undo вставки — **вся вставленная фигура** (структурный шаг: undo — `shape_delete`, redo — `shape_restore` с diagram и детьми). Запрос `smartArt.nodes` отвечает **сервер** (явный allowlist серверных запросов; произвольная движковая команда недоступна): `query {id, cmd, target, params}` разрешает слайд и фигуру по ключам сессии, гоняет движковый запрос по авторитетному состоянию и отвечает `query_result {id, version, result | error}` только спросившему; version, журнал и undo не меняются, viewer спрашивать может, а изменяющая, неизвестная или не входящая в allowlist команда — ошибка в ответе. Три конверсии — отдельный структурный срез: `smartArt.fromText` несёт **весь** `Diagram`, который построил движковый `from_text_plan` из абзацев и уровней исходной фигуры, и итоговый бокс; `smartArt.toText` — **весь** `TextBody`, который построил `to_text_plan` (уровни, маркеры, размеры заголовков и пунктов), и бокс; `smartArt.toShapes` значения не несёт, только адресует группу. Движок проверяет значение (layout/style/colors, число узлов, текст и JSON диаграммы; размер, число абзацев и ранов тела; конечность и положительность бокса) **до первой записи** и заменяет исходную фигуру на её месте в z-order одним структурным шагом; образ undo — **вся исходная фигура** (текстовая или группа с diagram и детьми и их id), поэтому redo возвращает ровно результат конверсии. Картинка в узле — отдельный срез по медиа-каналу: `smart_art_picture` несёт только `sha256`/`name` объекта, уже лежащего в канале, и **итоговое** место картинки (crop и alpha); байты идут `PUT`/`GET /media/{sha256}`, как у `insert.picture`, поэтому операция остаётся маленькой. Нормализатор адресует верхнеуровневую группу и верхнеуровневый узел (подпункт сводится к своему верхнему узлу, как в одиночной команде) и отказывает до отправки при обычной фигуре, вложенной группе, несуществующем узле, неверном дайджесте и месте без видимой площади. Движковая `smartArt.setPicture` до первой записи проверяет цель (верхнеуровневая группа), узел, allowlist и бюджет картинки, конечность crop и положительную видимую площадь, `alpha` в 0..=1 и неизменность layout; затем ставит байты тем же `add_media`, что и вставка картинки (дедуп по содержимому и один и тот же порядок id на всех репликах), записывает место в узел и регенерирует рисунок. Место хранится в модели (`DiagramNode.picture_place`) и пишется в data-часть как `a:srcRect` узла. Образ undo — **вся группа** (`shape_field{field: smartArt}`), поэтому undo возвращает исходный узел с его детьми и прежней картинкой, а redo — результат; в срез не входит только камера/сцена 3-D модели и относительные эффекты.

Диаграммы идут тем же правилом: `chart_set` несёт **весь** итоговый `Chart` — тип, категории (с внешними уровнями), серии (имена, значения, форматирование), опции элементов, style/palette и сохранённые части. Команды `chart.type`, `chart.data` и `chart.options` нормализуются на клиенте через движковый `chart::plan` — ту же функцию, которой пользуются одиночные команды (`insert.chart` строит из неё сэмпл и применяет типизированные данные), — поэтому на проводе ровно то значение, которое одиночная команда оставила бы, а не аргументы, которые каждая реплика слила бы со своей (возможно, импортированной) копией. Адаптер требует фигуру-чарт и ограничивает значение до первой записи; движковая `chart.setWhole` десериализует модель, проверяет тип, число категорий, серий и точек, длины текста и размер JSON (192 KiB) и только потом заменяет чарт. Вставка совместная тоже: `chart_insert` несёт **весь** чарт, который создала бы команда, и итоговый бокс, поэтому все реплики создают один и тот же чарт, а не свой сэмпл; undo вставки — обычный структурный шаг фигуры. Образ undo правки — **вся фигура чарта** (`shape_field{field: chart}`, модель `Shape` в JSON вместе с боксом): команды чарта выражают только часть модели, а сохранённая часть (встроенная книга, drawing) из аргументов не воспроизводится, поэтому чужая правка того же чарта после шага даёт `undo-conflict`. Значение, не влезающее в 192 KiB из-за сохранённых частей, отклоняется `invalid` до записи; перенос этих частей в медиа-канал — следующий шаг.

`arrange.align` и `arrange.distribute` — исключение из этого правила, потому что это одна пользовательская команда над несколькими объектами и её undo обязан отменять шаг целиком. Клиент считает итоговые боксы сам, через движковые `align_plan`/`distribute_plan` — ту же арифметику, что использует одиночная команда (край слайда, рамка выборки, равные промежутки), и отправляет **одну** `shapes_set_bounds`. Адаптер прогоняет движковую `shape.setBoundsMany`: она проверяет все id и дубликаты до первой записи, клампит значения и пишет геометрию в одном `edit`, поэтому вся выборка — один version и один шаг undo. Фигуры, чей бокс не меняется, в операцию не попадают; если не меняется ни одна, клиент не отправляет ничего.

`slide_transition` несёт **весь** переход, а не аргументы `transition.set`: команда сохраняет тайминги показа, встроенный звук и сохранённый `raw` того значения, которое заменяет, поэтому две реплики, применившие одни аргументы к разному состоянию, разошлись бы. План итогового значения считает движковая `transition.set_plan` — та же функция, которой пользуется одиночная команда (эффект, опция по умолчанию, длительность по умолчанию, схлопывание `none` в отсутствие перехода). Адаптер прогоняет `slide.transition.set`: команда десериализует модель, принимает неизвестный модели эффект только вместе с сохранённым XML, проверяет звук по `doc.media` и пишет значение одним `edit`; `null` — это «нет перехода». Это и есть точный образ шага undo (§6), поэтому undo/redo несут ту же операцию с прежним значением.

`shape.fill`, `shape.line` и `format_set` входят в per-user undo с точным образом значения (§6): undo/redo несут само значение модели в `shape_field`, а не повторяют пользовательскую команду, потому что `shape.fill`/`shape.line`/`format.*` выражают только часть модели (tile и scaled градиента, custom dash, форматирование ранов). `shape_field` — операция истории, а не пользовательская: адаптер принимает её только как undo/redo и только с тем значением, которое записал последний шаг актора.

`shape_animations` — тот же приём для шагов анимации. `animation.add`/`animation.remove` нормализуются в **полный список шагов одной фигуры**: новый шаг строит движковая `animation.add_plan` (та же `build`, что у одиночной команды), поэтому каждая реплика получает одинаковые preset-id, тайминги, цвета и motion path, которых аргументы `animation.add` не повторяют. Одна операция адресует одну фигуру (выборка из нескольких — отказ). Адаптер резолвит ключи слайда и фигуры (неизвестный ключ, фигура с другого слайда или отсутствующая — отказ до первой записи), принудительно ставит id фигуры в каждом значении и прогоняет `slide.animation.set`: команда ограничивает список (256 шагов, 64 KiB), принимает только поля модели, требует известный эффект и заменяет шаги фигуры на месте первого; шаги других фигур сохраняют позиции, `[]` очищает. Список — точный образ шага undo (§6), поэтому undo/redo несут его же.

`slide_animations` — полная последовательность **слайда** для `animation.set`, `animation.timing`, `animation.move`, `animation.options`, `animation.clear` и `animation.painterApply`. Эти команды меняют не только шаги одной фигуры: `animation.move` ставит шаг за шаг другой фигуры, а `animation.set` на выборке заменяет шаги нескольких фигур в их местах, поэтому список одной фигуры (`shape_animations`) не выразил бы перемежение. Каждая реплика считает итоговую последовательность движковыми планами `animation::set_plan`/`timing_plan`/`move_plan`/`options_plan`/`painter_plan` — теми же функциями, на которых работают одиночные команды (поэтому `none` сохраняет место первой фигуры, тайминги клампятся так же, `to` клампится к концу, а опция разрешается по словарю своего эффекта одинаково на всех репликах). `animation.clear` адресует слайд, чью последовательность очищает, а не тот, на который смотрит отправитель. Кисть анимации — значение сессии, а не документа (`anim_painter` в движке): `animation.painterApply` отправляет **итоговую** последовательность адресованных фигур, посчитанную той же `painter_plan` (собственные шаги цели заменяются, абзацный шаг без такого абзаца у цели становится шагом всей фигуры), поэтому репликам не нужна кисть, а отправитель снимает одноразовую кисть после отправки, как одиночная команда. Операция адресует слайд и не несёт ключ фигуры; команда `slide.animations.set` ограничивает список (4096 шагов, 192 KiB), принимает только поля модели, требует известный эффект и проверяет, что **каждая** названная фигура ещё на слайде, до первой записи, затем заменяет последовательность целиком. Команда, чей результат совпадает с текущей последовательностью, не отправляет операцию. Последовательность — это и есть точный образ шага undo (§6): перед и после — весь упорядоченный список слайда, поэтому любая смена анимации этого слайда после шага (в том числе чужой фигуры) даёт `undo-conflict`, а смена шагов другого слайда — нет.

Заметки слайда — отдельный адрес: у них нет фигуры, поэтому `notes_set`/`notes_insert`/`notes_delete` несут только `target.slide`. `slide.notes` нормализуется в `notes_set` с **полным** телом: `body` панели заметок берётся как есть, `text` применяется к текущему телу той же `replace_text`, что и одиночная команда, поэтому на проводе всегда целый `TextBody`, а undo кладёт обратно и текст, и раны. Печать в панели заметок (`text.insert`/`text.delete`/`edit.delete` с `notes: true`) нормализуется в `notes_insert`/`notes_delete` со смещением в символах; сервер перебазирует смещение по журналу, как для текста фигуры (§4.4), но по адресу `(слайд, тело заметок)`: правка заметок другого слайда не сдвигает эту, а замена тела после базы отправляет операцию в `stale` и клиент перечитывает тело. Адаптер резолвит ключ слайда до первой записи (удалённый слайд — `stale`), прогоняет одиночную команду и **возвращает выделение получателя** на место: правка заметок не сбрасывает каретку, а каретка в том же теле заметок сдвигается на вставленные или удалённые перед ней символы. Образ шага undo — всё тело заметок до и после (§6).

То же правило у `shape_fields` (шаг группы: один образ на каждое изменившееся звено), `shape_restore` (structural undo фигуры: полный образ фигуры, её места в z-order и анимаций), `slide_restore` (structural undo слайда: полный образ слайда), `slide_transition` (образ шага `transition.set`: полный переход, включая сохранённый XML), `shape_animations` (образ шага `animation.add`/`animation.remove`: полный список шагов фигуры) и `slide_animations` (образ шага `animation.set`/`animation.timing`/`animation.move`: полная упорядоченная последовательность слайда). `slide_transition`, `shape_animations` и `slide_animations` — одновременно и пользовательские операции, и образы шага: без `history` это обычная правка, а в undo/redo `check_restore` принимает их только с тем значением, которое записал последний шаг актора. Все эти операции строит только сервер из своей истории; `check_restore` сверяет и адрес (слайд, фигура, список фигур), и payload с записанным образом, поэтому клиент не может через undo подменить объект или значение. Для undo `slide.new`/`slide.duplicate` обратная операция — обычный `slide_delete`, для undo `shape.insert`/`insert.picture`/`insert.video`/`insert.audio` — `shape_delete`; обе тоже проверяются по истории.


Документный шрифт (`p:embeddedFontLst`) — значение презентации, а не слайда: у него нет ни слайда, ни фигуры в адресе, и он не сдвигает ни один адрес или ключ. `font.create` несёт имя гарнитуры, слот лица (`regular`/`bold`/`italic`/`boldItalic`) и `sha256` файла; сами байты идут медиа-каналом, как у картинки, поэтому операция остаётся маленькой, а одинаковый файл хранится один раз. Адаптер достаёт байты из медиа-кэша (их нет — `unsupported` с `retryable`, клиент докачивает и повторяет), проверяет, что объект именно шрифт, и прогоняет `font.create`: команда валидирует sfnt-заголовок и каталог таблиц, кладёт байты в `doc.media` (`application/x-fontdata`) и ставит id в названный слот записи, создавая её при отсутствии; гарнитуры сравниваются без учёта регистра, поэтому вторая гарнитура с тем же именем в другом регистре не появляется. `font.set` несёт дескрипторы (`panose`, `pitchFamily`, `charset`) как итоговые значения, `font.remove` убирает запись целиком; обе отклоняют отсутствующую запись до первой записи, а медиа-объект лиц при удалении остаётся — на него может ссылаться образ undo. `font.restore` — операция истории: полная модель `EmbeddedFont` с id четырёх лиц (или `null`, если записи не было), её строит сервер из истории актора, и `check_restore` принимает её только с тем значением, которое записал последний шаг. `slideKey`/`shapeKey` в target такой операции запрещены: адрес — сама гарнитура. Все три пользовательские операции — merge-класс: они не двигают адреса, и две одновременные операции над разными лицами одной гарнитуры обе применяются.

Трёхмерные модели (срез 2026-11-10) идут по тому же медиа-каналу: `media_insert` с `kind: model` несёт `sha256` бинарного glTF (`.glb`), `name` и итоговый `rect?`, а адаптер прогоняет движковую `insert.model3d`. Allowlist — одна подпись (`glTF` + версия 2 + длина ≥ 12 байт), потому что Office кладёт в пакет именно `.glb`-часть (`p:contentPart` с отношением `model3d`); JSON-`.gltf` с отдельными буферами частью пакета быть не может и отклоняется. Бюджет у моделей **свой** (`MAX_MODEL_*`: 32 МиБ на объект, 16 объектов и 128 МиБ на сессию), поэтому большая модель не вытесняет картинки, аудио и шрифты; `GET /media/{sha256}` отдаёт её как `model/gltf-binary` по подписи. Клиент загружает байты до операции (как у картинки), сервер хранит объект по дайджесту и достаёт его из кэша сессии или из хранилища, а реплика без байтов получает `unsupported` с `retryable` и докачивает. Модель на слайде — фигура `Model3d { media, poster? }`: часть пакета копируется в файл без изменений, а рисуется либо `mc:Fallback`-постер, если он был в импортированном файле, либо заглушка (изометрический куб на рамке фигуры). Поэтому известное ограничение коммита теперь звучит как «нарисована постером или заглушкой, а не отрендеренной моделью», а не «не рисуется». Undo вставки — обычный структурный шаг фигуры (обратная операция — `shape_delete`, redo — `shape_restore` с полным образом фигуры): вставка добавляет одну фигуру наверх z-order. Камера модели — отдельный срез по правилу одного итогового значения: `model3d.camera` несёт **всю** итоговую камеру (`position`, `target`, `up` в EMU слайда и `fov` в градусах) или `null` (вид читателя по умолчанию), относительной формы у операции нет — две реплики, применившие «повернуть на 15°» к своим видам, разошлись бы. Нормализатор гоняет ту же движковую `camera_param`, что и одиночная команда, поэтому относительное поле, вырожденная камера (совпадающие `position`/`target`, нулевой или параллельный взгляду `up`, `fov` вне 1–179°) и обычная фигура отклоняются до отправки, а тип на проводе запрещает неизвестные поля, так что враждебный кадр — это плохой кадр, а не тихое слияние. Движковая `model3d.camera` проверяет то же до первой записи. Камера живёт в модели (`ShapeKind::Model3d { camera }`) и пишется в slide-часть как `am3d:camera` рядом с content part (`am3d:pos`, `am3d:up`, `am3d:lookAt`, `am3d:perspective fov` в 1/60000 градуса) и читается обратно точно; отсутствие камеры — вид по умолчанию. Образ undo — **вся фигура модели** (`shape_field{field: model3d}`), поэтому undo возвращает вид и все остальные поля объекта, а чужая правка модели после шага даёт `undo-conflict` без записи.
Сцена модели — следующий срез по тому же правилу одного итогового значения: `model3d.scene` несёт **всю** сцену — один свет (`type`, `direction`, `intensity` и `angle` конуса только у `spot`) и окружение (`ambient`, необязательный sRGB-фон) — или `null` (сцена читателя по умолчанию); относительной формы (`dimmer`, `rotate`, `zoom`) у операции нет, потому что две реплики, применившие «темнее» к своим сценам, разошлись бы. Нормализатор гоняет ту же движковую `scene_param`, что и одиночная команда, поэтому относительное поле, неизвестный тип света, нулевое направление, значения вне диапазонов и несовпадение `angle` с типом отклоняются до отправки, а тип на проводе запрещает неизвестные поля. Движковая `model3d.scene` проверяет то же до первой записи. Сцена живёт в модели (`ShapeKind::Model3d { scene }`) и пишется в slide-часть как `am3d:scene` рядом с камерой (`am3d:light` с `type`/`intensity`/`angle` и `am3d:dir`, `am3d:environment` с `ambient`/`color`; интенсивность и ambient — в тысячных процента, угол — в 1/60000 градуса) и читается обратно точно; отсутствие сцены — освещение по умолчанию. Образ undo — та же **вся фигура модели**, а чужая правка модели после шага даёт `undo-conflict` без записи.

### 3.3 Идентификаторы (ADR-0002)

- `slideKey` — UUID, выдаётся сервером при первом входе в сессию для каждого
  слайда; живёт в карте, не в файле. `SlideId` модели остаётся локальным ключом
  внутри сервера.
- `shapeKey` — сервер использует `ShapeId.0` (файловый `cNvPr`), если он
  уникален **в слайде**; иначе и для вставленных — новый UUID. Совет из
  ADR-0002 «сервер следит за уникальностью» реализуется проверкой при join:
  `pptx/src/read/shapes.rs:22-50` гарантирует уникальность только внутри части,
  `cmd/arrange.rs:240` прямо отмечает повторы между слайдами.
- `MediaId` — по `sha256` содержимого; локальный `MediaId.0` выдаёт сервер
  (`Presentation::alloc_id`, `model/src/lib.rs:1036`). Два клиента, вставивших
  одну картинку, дают один медиа-объект.
- **Порядок адресуется якорем**, не числом (ADR-0002 §5): `{before:shapeKey}`
  или `{after:shapeKey}` для z-order и порядка слайдов.
- `tmpId` клиента допустим только до `applied`; объект, созданный операцией,
  получает серверный ключ в результате.
- Надгробия: операция по удалённому `slideKey`/`shapeKey` →
  `rejected{code:"stale", retryable:false}`; объект не воскресает.

## 4. Протокол

### 4.1 Транспорт

WebSocket over TLS (WSS), один набор сообщений на пять приложений
(ARCHITECTURE §2). JSON-фрейм (текст), потому что операции — уже JSON
(`serde_json::Value`), а бинарь медиа идёт отдельным каналом.

- Лимиты: сообщение ≤ 256 KiB (операции DeckCraft — сотни байт; крупнее только
  `delta` после массовой вставки); ≤ 16 соединений на документ (5 участников +
  служебные); ≤ 50 операций/с на актора; `presence` ≤ 1 KiB и ≤ 10 Гц.
  Списки внутри операции ограничены явно: `format_set` — ≤ 4096 адресов,
  `table_cell_fill` — ≤ 4096 ячеек, `cells_text` (образ шага над N ячейками) и
  `slide_animations` (последовательность слайда) — ≤ 4096 шагов/тел и
  ≤ 192 KiB JSON; иначе `invalid`, потому что такая операция и её undo всё
  равно не влезли бы в лимит.
- Desktop: `tokio-tungstenite` + `rustls` (лицензии MIT/Apache-2.0 — в
  allowlist). Web: WebSocket из `web-sys`/`ewebsock`, потому что в браузере нет
  TCP (`apps/deckcraft-web/src/main.rs:1-14`).
- Медиа **не** едет в операциях: отдельная загрузка по `sha256`
  (`PUT /v1/sessions/{id}/media/{sha256}`, чтение `GET /media/{sha256}`), в
  операции — только `{sha256, name, rect?}` (и `kind` для видео/аудио/3-D
  модели). Сервер хранит один объект на дайджест; клиент загружает байты до
  операции и подтягивает чужие по `GET /media/{sha256}`. Путь `GET /media`
  нормализуется (хвостовой `/`, query и расширение вроде `.glb` не входят в
  имя), а `Content-Type` ответа выбирается по подписи сохранённых байт, а не по
  запрошенному имени, поэтому один и тот же объект отвечает одинаково из памяти
  и после рестарта.
- Allowlist медиа — по подписи (не по расширению, кроме контейнеров с общей
  подписью): PNG/JPEG/GIF/WebP/BMP/TIFF/SVG ≤ 8 МиБ, 512 объектов и 64 МиБ на
  сессию; MP4/MOV/WebM/AVI и WAV/FLAC/Ogg/MP3/M4A/AIFF/MIDI ≤ 32 МиБ, 32
  объекта и 192 МиБ на сессию; sfnt-лица шрифтов ≤ 16 МиБ, 32 объекта и 64 МиБ
  на сессию; бинарный glTF (`.glb`: magic `glTF`, версия 2) ≤ 32 МиБ, 16
  объектов и 128 МиБ на сессию. Счётчики и лимиты раздельные, чтобы большие
  клипы и модели не вытесняли картинки.
- HTTP-клиент медиа у desktop-клиента повторяет схему WebSocket-URL: `ws://` →
  TCP, `wss://` → `rustls` с системным хранилищем корней (`rustls-native-certs`,
  `SSL_CERT_FILE`/`SSL_CERT_DIR` учитываются). Порт по умолчанию 80/443,
  `Host` без порта по умолчанию, IPv6 — в скобках.

### 4.2 Сообщения

| Тип | Направление | Поля | Семантика |
|---|---|---|---|
| `hello` | C→S | `v, app:"deckcraft", doc, jwt, client` | handshake; JWT только здесь |
| `welcome` | S→C | `sessionId, actorId, role, lease, version, snapshot, capabilities` | `capabilities.kinds=["command","structural"]`, лимиты |
| `op` | C→S | `opId, doc, baseVersion, kind, target, payload, preview?` | операция |
| `applied` | S→C | `opId, version, result{command,delta}, actorId` | авторитетный результат |
| `rejected` | S→C | `opId, code, retryable, hint{version}` | `stale\|conflict\|forbidden\|invalid\|auth\|lease` |
| `presence` | C↔S | `slide, shapes[], text{anchor,caret}, viewport` | не журналируется, без ack |
| `resync` | C→S | `lastVersion` | запрос базы/хвоста после разрыва |
| `query` | C→S | `id, cmd, target, params?` | read-only запрос из allowlist (`smartArt.nodes`) к авторитетному состоянию; ответ — только спросившему |
| `query-result` | S→C | `id, version, result \| error` | ответ на `query`; version, журнал и undo не меняются, viewer может спрашивать |
| `snapshot` | S→C | `version, snapshot{mode,cursor}, base{version,bytesBase64?,keys,chunks?}, tail[]` | ответ на `resync`; `mode:"base"` — реплика заменяется базой; `chunks` — база идёт кусками (§4.5.1) |
| `base-chunk` | C→S | `version, index` | запрос одного куска базы, объявленной в `snapshot`; read-only, как `query`: версия и журнал не меняются, viewer может спрашивать |
| `base-chunk` | S→C | `version, index, count, data` | кусок базы (`data` — base64); `index`/`version` эхом, чтобы опоздавший ответ старой цепочки игнорировался; отказ — `rejected{code:"stale"}` (базу сменила компакция) или `invalid` (куска нет) |

| `error` | S→C | `code, message, retryable` | фатальные ошибки соединения |
| `ping`/`pong` | C↔S | — | heartbeat и продление lease |

`epoch` в конверте допускается, но DeckCraft его не использует: адрес — ключ, а
не индекс (ADR-0002 §5, ответ deckcraft на ревью pdfcraft).

### 4.3 Порядок и версии (ADR-0003)

- Один монотонный `version` на документ; клиент применяет строго по
  возрастанию; пропуск → `resync`.
- `opId = UUID`; сервер хранит окно дедупа (10 000 записей или 24 ч). Повтор
  возвращает прежний `applied` **без** исполнения: `shape.move {x,y}` после
  повторного применения даст неверное положение, а `text.insert` — дубль.
- `baseVersion` — контекст, не блокировка: merge-операции применяются к head,
  ответ несёт `conflict:true`, если `baseVersion < head`.
- `structural` требует `baseVersion == head`; иначе `rejected{code:"stale",
  retryable:true, hint:{version}}` и клиент перечитывает состояние.

### 4.4 Конфликты (ADR-0004)

| Ситуация | Класс | Политика | Что видит пользователь |
|---|---|---|---|
| двое двигают одну фигуру | merge | серверный порядок; `xfrm` целиком, last-writer-wins | фигура на месте последнего; без тоста |
| двое двигают **разных** детей одной группы | merge | обе операции; рамка группы пересчитывается локально (`refit_groups`) | группа растянулась, дети на своих местах |
| двигают ребёнка и одновременно `arrange.group/ungroup` | structural | group/ungroup эксклюзивен; движение при stale → `stale` | группа меняется, движение повторяется |
| двое меняют z-order | structural | `arrange.reorder`/`bring*` эксклюзивны (порядок — `Vec<Shape>`) | второй получает `stale` и повторяет |
| удаляют слайд, пока на нём правят фигуру | structural | удаление эксклюзивно и первым; запоздавшая правка → `stale, retryable:false` | «слайд удалён», правка отброшена |
| двое печатают в одном абзаце | merge | серверный порядок + сдвиг `(paragraph,char)`; позиция недостижима → `conflict` | текст обоих, курсор переставлен |
| двое форматируют перекрывающиеся диапазоны | merge | серверный порядок; значения абсолютные, побеждает последняя операция на общих символах | оба видят одно и то же форматирование |
| диапазон форматирования удалён чужой правкой | merge | оба смещения перебазируются; пустой диапазон → `invalid` до записи | «текст изменён», операция отброшена, документ не тронут |
| правят одну ячейку таблицы | merge | как текст, адрес `(shape, cell, paragraph, char)` | оба текста, last-writer-wins по символу |
| двое меняют разные свойства фигуры | merge | сливаются (fill и xfrm независимы) | оба изменения |
| вставляют разные картинки с одним именем | merge | разные `MediaId` (sha256), имя — значение | обе картинки |
| второй шлёт `animation.add` для удалённой фигуры | merge | `stale`, объект не воскресает | «объект удалён» |
| viewer шлёт `op` | — | `rejected{code:"forbidden"}` | UI заблокирован заранее |

Правила, без которых таблица не работает:

- **Производное не пересылается**: `refit_groups`, `reroute`, autofit, порядок
  z-order как число. Пересылается намерение (`xfrm` ребёнка, якорь
  перестановки), результат считается на каждой реплике (ADR-0001 §4).
- **Содержимое пересылается**: значения полей, которые обязаны совпадать у всех
  (в DeckCraft — свойства фигур/текста; в GridCraft — значения формул). Это
  уточнение принято в ревью gridcraft `20261106T151245Z-gridcraft-bcda`.
- **`regroup` в совместном режиме отключён**: он ищет предыдущий Ungroup в
  локальной истории (`cmd/arrange.rs:373-386`), которой у другого клиента нет.

### 4.5 Reconnect и догон

1. Клиент переподключается, шлёт `hello` с `lastVersion`.
2. Если `lastVersion` в хвосте журнала — сервер отдаёт `applied`-записи
   начиная с `lastVersion+1` (по возрастанию `version`).
3. Иначе — `resync`: `snapshot {version, base{version, bytesBase64?, keys, chunks?}, tail[]}`;
   клиент заменяет состояние базой и проигрывает хвост выше неё, непринятая
   очередь сбрасывается. `bytesBase64` отсутствует, если база больше лимита
   `max_base_inline` (8 MiB, `COLLAB_MAX_BASE_INLINE`): тогда база приходит
   кусками (§4.5.1) — клиент собирает её сам и заменяет реплику, не переоткрывая
   файл из кабинета. Если база больше и цепочки (`max_base_chunks`), сервер
   называет её без байтов, и клиент переоткрывает файл из кабинета (запасной
   путь, он же путь для клиента, который не умеет цепочку).
4. База несёт карту ключей сессии (`slides`, `shapes`, `dead`, `next`): ключи
   выдаются в порядке обхода и после структурных правок из документа не
   выводятся (ADR-0002). Реплика, загрузившая базу, продолжает нумерацию с
   `next`, поэтому следующая вставка получает тот же ключ, что и на сервере.
5. Непринятые локальные операции повторяются **с теми же `opId`** → дедуп.
   Ставшие невалидными (адрес удалён, `baseVersion` структурной устарел) →
   `conflict` в UI, без молчаливой потери. Замена реплики базой — исключение:
   правка, не дошедшая до сервера, не переносится на базу.
6. Повторный `hello` не сбрасывает per-user undo: история живёт на сервере до
   TTL (ADR-0010).

#### 4.5.1 База в кусках (выше `max_base_inline`)

Кадр снапшота ограничен теми же лимитами, что и любой другой (`Limits::max_message_bytes`),
а нативная база деки из 100+ слайдов с медиа — это десятки мегабайт: фотографии лежат в базе
байтами, а не ссылками. Поэтому база выше `max_base_inline` едет **цепочкой кусков**, которую
клиент вытягивает по одному:

- `base.chunks = {sha256, len, chunkSize, count}` — дайджест всей базы, её размер в байтах,
  размер куска и глубина цепочки (`ceil(len / chunkSize)`). `bytesBase64` в этом случае нет.
- Клиент спрашивает `base-chunk {version, index}`; сервер отвечает `base-chunk
  {version, index, count, data}`, где `data` — base64 куска
  `bytes[index*chunkSize .. min((index+1)*chunkSize, len)]`. В кадре одновременно не больше
  одного куска: клиент просит следующий только после предыдущего, поэтому кадр остаётся
  предсказуемым при любом размере базы.
- Собранная база проверяется дважды: размер (`len`) и дайджест (`sha256`, как в медиа-канале).
  Несовпадение — цепочка бросается, `lastError` показывает причину, реплика остаётся прежней.
- **Лимиты — на обеих сторонах.** Сервер: `max_base_chunk` (`COLLAB_MAX_BASE_CHUNK`, 1 MiB) и
  `max_base_chunks` (`COLLAB_MAX_BASE_CHUNKS`, 1024). Клиент: `BaseChunks::MAX_CHUNK_SIZE`
  (8 MiB), `MAX_COUNT` (4096), `MAX_LEN` (64 MiB) и проверка `count == ceil(len/chunkSize)`.
  Цепочка вне этих пределов отвергается **до** любой аллокации: даже доверенному серверу
  реплика не выделяет память по объявленному числу.
- **Возобновление.** Клиент хранит собранный префикс и индекс, который ждёт. Обрыв сокета
  сбрасывает только ожидающий запрос: после `hello` клиент просит тот же `index`, а не первый
  кусок. Если `hello` показал, что версия ушла вперёд, `resync` приносит снапшот заново; если
  это та же база (тот же `version`, `sha256`, `chunkSize`, `count`), цепочка **продолжается**,
  иначе начинается с нуля.
- **Смена базы.** Компакция заменяет снапшот: кусок старой версии — `rejected{code:"stale",
  retryable:true}`, и клиент вместо доигрывания цепочки просит новый `resync`. Так клиент
  никогда не смешивает байты двух баз.
- **Пока база собирается, реплика — старый документ.** `Applied`, пришедшие в это окно, не
  двигают реплику и не теряются: после установки базы клиент сам просит хвост от версии базы
  (`resync`), и он получает шаги выше неё. Новые правки в этом окне не принимаются
  (`submit` → `rebuilding`): нормализовать команду по документу, которого в комнате уже нет,
  нельзя.
- **Счётчики.** `base_transfers_total` считает выданные снапшоты с базой, `base_chunks_total` —
  выданные куски, `base_bytes_total` — только inline-байты (для цепочки остаётся 0). Размер
  базы виден в логе `resync` и в гейтах.

Запасной путь «база названа без байтов» остаётся: он нужен клиенту, который не знает
`base-chunk` (старая сборка), и базе, которая не влезает даже в цепочку. Совместимость
поэтому не требует новой версии конверта: `PROTO_VERSION` остаётся 1, `chunks` и
`base-chunk` — аддитивные поля и тип сообщения. Старый клиент, получив снапшот с `chunks` и
без `bytesBase64`, ведёт себя как раньше — сообщает «переоткройте файл из кабинета»; новый
клиент со старым сервером цепочку просто никогда не увидит.

### 4.6 Снапшоты и compaction (ADR-0005)

- Снапшот = `.deckcraft` (`presentation.json` + `media/` + `chart-parts/`) +
  метаданные `{version, actor, savedAt, keys, fileId, baseFileETag}`.
- Частота: каждые 200 операций или 60 с, и обязательно перед подключением
  нового участника, если хвост > 1000 записей. `resync` берёт снапшот на месте,
  если сохранённая база старше пропуска клиента или хвост выше неё не сплошной;
  так вытеснение хвоста никогда не оставляет клиента без пути назад.
- В снапшоте едут байты `.deckcraft` и карта ключей; хвост выше базы — обычные
  `applied`. Выше `max_base_inline` — цепочка кусков (§4.5.1). Счётчики сервера:
  `base_transfers_total`, `base_chunks_total`, `base_bytes_total` (inline-байты).
- Снапшот помнит `sha256` своей базы: цепочка объявляет его в `base.chunks.sha256`,
  и клиент проверяет собранное до замены реплики.
- Хранятся 2 снапшота (предыдущий — на случай частичной записи); хвост журнала
  обрезается по версии старого снапшота.
- Восстановление: загрузка базы → реплей хвоста → `version` = HEAD. session-
  ключи берутся из карты (в снапшоте — из `keys`), не из файла.
- Медиа хранится по `sha256` отдельно от базы; удаление медиа — только когда на
  него нет ссылок (`engine/src/media_refs.rs` даёт полный обход) и истёк TTL
  надгробия.
- Снапшот не логируется, не уходит в кабинет; лимит размера — как у ридера
  (`crates/format` ограничивает inflate манифеста).

## 5. Presence (ADR-0006)

Тот же WS, тип `presence`, 10 Гц, ≤ 1 KiB, drop-stale, TTL 30 с, без ack и без
журнала.

```json
{"type":"presence","slide":"<slideKey>","shapes":["<shapeKey>"],
 "text":{"anchor":[p,ch],"caret":[p,ch],"cell":[r,c]},
 "viewport":{"zoom":1.0,"x":0.0,"y":0.0},"color":"#3b82f6"}
```

- Поля совпадают с `Selection` (`engine/src/lib.rs:148-164`), поэтому не нужен
  второй способ адресации: presence и операции говорят на одном языке.
- Цвет — детерминированно из `actorId`; имя — из JWT (`sub`), не из сообщения.
- Backpressure: сервер хранит последнее состояние на актора и рассылает
  последнее; промежуточные кадры отбрасываются.
- Viewer тоже видит presence и отправляет свой (активный слайд).

## 6. Undo/redo на пользователя (ADR-0010)

- **Требование:** undo актора отменяет только его операции; чужие правки
  остаются. Undo — новая операция с `baseVersion = head`, проходит проверки
  роли/lease/конфликтов и получает новый `version`.
- **Механизм DeckCraft:** локальная история снимков `Arc<Presentation>`
  (`HistoryEntry.doc`, `engine/src/lib.rs:167`) + `author` в журнале сервера.
  Снимок O(1) по указателям; правка — O(один слайд).
- **Отдельный путь применения чужих операций.** Сегодня `execute_unguarded`
  пушит undo автоматически для любой `undoable` команды
  (`engine/src/lib.rs:683-691`). Добавляется `Session::apply_remote(...)`,
  который исполняет нормализованную команду и **не** пишет `HistoryEntry` и не
  входит в `journal` пользователя.
- Undo шага: берём свой снимок, вычисляем инверсию затронутых полей (адреса —
  ключи), отправляем как операцию. Если затронутое изменено другим после шага —
  `rejected{code:"undo-conflict"}`, без молчаливой перезаписи.
- **Образ значения.** Шаг хранит before/after-образ одного объекта: `xfrm`,
  текст (plain для `text.set`/`text.insert`/`text.delete`), fill, outline и
  целый `TextBody` для `format.*` (тело фигуры, одной ячейки таблицы или
  каждой из N адресованных ячеек). Первые три восстанавливаются обычными
  командами (final values). Fill, outline и тело фигуры восстанавливаются
  payload `shape_field{field, value}`: значение —
  сама модель в JSON, потому что `shape.fill`, `shape.line` и `format.*`
  покрывают только её часть. Тело ячейки восстанавливается `cell_text{cell, body}`
  (`shape.setField{field: cellText, cell}`), а тела N ячеек — `cells_text{cells}`
  (`shape.setCellBodies`, по одному `shape.setField` на ячейку в одном шаге),
  чтобы undo не переписывал соседние
  ячейки: образ шага адресован `(слайд, фигура, row, col)` на каждый адрес. Сервер
  строит `shape_field`/`cell_text`/`cells_text` из своей истории; адаптер принимает их лишь как
  undo/redo своего шага и только с тем значением, которое шаг записал (иначе —
  `invalid`). `shape.setField` в движке ставит значение обратно, ограничив
  размер и провалидировав JSON в тип модели.
  Шаг `format.*` по диапазону ранов или по каретке хранит **то же** целое тело
  фигуры или ячейки: формат расщепляет раны на границах, и точный прежний набор
  ранов описывает только всё тело. Поэтому undo возвращает прежние раны (и
  остальные тоже, они не менялись), а любая чужая правка этого тела после шага
  даёт `undo-conflict` — диапазон не восстанавливается поверх чужого текста.
  У шага над N ячейками образ — тело каждой из них, поэтому чужая правка **любой**
  адресованной ячейки делает undo `undo-conflict`, не трогая ни одну.
  Шаг `table_style`/`table_options`/`table_cell_fill`/`table_merge`/`table_split`/
  `table_column_width`/`table_row_height` хранит **всю таблицу**
  (`shape_field{field: table}`), как и шаг строки/столбца: команды `table.*`
  не выражают прежнее значение (заливка ячейки — это `Option<Fill>`, слияние
  меняет и текст), а образ всей таблицы точен. Поэтому чужая правка этой
  таблицы после шага (в том числе текст в её ячейке) даёт `undo-conflict`, а
  undo возвращает и таблицу, и её бокс.
  Шаг SmartArt (`smartArt.setNodes`/`addNode`/`removeNode`/`promote`/`demote`/
  `layout`/`style`/`colors`) хранит **всю группу** (`shape_field{field: smartArt}`):
  правка контура регенерирует детей с новыми id и заменяет drawing
  импортированного файла, поэтому значение diagram само шаг не восстанавливает;
  образ группы возвращает и контур, и детей с их id. Чужая правка той же группы
  после шага даёт `undo-conflict`.
  Шаг конверсии (`smartArt.fromText`/`toText`/`toShapes`) хранит **обе стороны
  замены**: всю исходную фигуру и всю получившуюся. Если id сохраняется
  (`toShapes`), restore сначала убирает слот, затем вставляет образ, поэтому
  замена с тем же id не конфликтует сама с собой; undo возвращает исходную
  фигуру целиком, redo — результат конверсии.
  Шаг картинки в узле (`smartArt.picture`) хранит **всю группу**
  (`shape_field{field: smartArt}`): установка картинки регенерирует детей с
  новыми id, поэтому значение diagram само шаг не восстанавливает, а образ
  группы возвращает контур, детей с их id и прежнюю картинку (или её
  отсутствие). Чужая правка той же группы после шага даёт `undo-conflict`; redo
  повторяет ту же операцию и ставит объект канала с тем же дайджестом, поэтому
  результат совпадает на всех репликах.
  Шаг диаграммы (`chart.type`/`chart.data`/`chart.options`) хранит **всю фигуру чарта**
  (`shape_field{field: chart}`): команды чарта выражают только часть модели, а сохранённая
  часть (встроенная книга, drawing) из аргументов не восстанавливается; образ фигуры
  возвращает тип, данные, опции и бокс. Чужая правка того же чарта после шага даёт
  `undo-conflict`. `insert.chart` — структурный шаг фигуры: undo — обычный `shape_delete`,
  redo — `shape_restore`.
- **Шаг группы.** `shape.fill`/`shape.line` по группе форматируют и всех её
  видимых участников. Шаг хранит образ на каждое изменившееся звено (сама
  группа и потомки, глубина ≤ 64) и восстанавливает их **одной** операцией
  `shape_fields{items:[{shape, field, value}]}` → движковая `shape.setFields`:
  значения валидируются и десериализуются до первой записи, поэтому сбой
  одного участника отказывает всей операции, а не оставляет половину группы
  перекрашенной. Неизменившиеся звенья в шаг не попадают.
- **Шаг выравнивания/распределения.** `arrange.align`/`arrange.distribute` двигают всю
  выборку одной командой, поэтому шаг хранит образ `xfrm` **на каждую сдвинутую фигуру** и
  восстанавливается **одной** операцией `shapes_set_bounds` → движковая
  `shape.setBoundsMany` (значения и адреса проверяются до первой записи). `same_state`
  сравнивает бокс каждого участника: если кто-то передвинул или изменил одного из них после
  шага, undo отказывает `undo-conflict` и не перезаписывает чужую правку.
- **Структурный шаг слайда.** `slide.delete` (а также undo `slide.new` и
  `slide.duplicate`) хранит полный образ слайда: модель в JSON, позицию и
  членство в секциях и custom show. Undo `slide.delete` — structural-операция
  `slide_restore{index, slide, sections?, shows?}`, redo — обычный
  `slide_delete`; и то и другое идёт через `check_restore` и требует
  `baseVersion == head`. Образ ограничен 192 KiB (лимит сообщения — 256 KiB),
  иначе undo отказывается `invalid`; id слайда и фигур сохраняются, чтобы
  операция была детерминированной на всех репликах.
- **Структурный шаг фигуры.** `shape.insert`, `insert.picture`,
  `insert.video`/`insert.audio` и `edit.delete` хранят **полный образ фигуры**:
  модель в JSON (id, текст, геометрия и прочие поля), группу-владельца и позицию
  среди её детей, а также анимации, которые называют фигуру или её потомков,
  включая эффекты чужих фигур, срабатывающие по ней как по триггеру. Образ
  группы уже содержит детей, поэтому шаг записывает только **верхние**
  удалённые фигуры: восстановление одной фигуры возвращает всё поддерево.
  Undo `shape.delete` — structural-операция
  `shape_restore{items:[{shape, parent?, index, value, animations?}]}`
  (как и `slide_restore`, требует `baseVersion == head` и идёт через
  `check_restore`; одна операция на весь шаг, атомарная в движке: значения
  валидируются и десериализуются до первой вставки, повтор id отказывает
  целиком), redo —
  обычный `shape_delete`. Undo `shape.insert` — обычный `shape_delete`, redo —
  `shape_restore`. `index` — позиция среди соседей, при восстановлении
  ограничивается текущей длиной списка, поэтому добавленные или удалённые
  соседи не мешают; `same_state` сравнивает содержимое, владельца и анимации,
  но не позицию, поэтому чужая правка соседа не блокирует undo, а чужая правка
  самой фигуры даёт `undo-conflict`. Ключи фигуры стабильны: карта ключей
  сохраняет обе стороны и после удаления, поэтому восстановленная фигура
  возвращается под тем же `shapeKey`.
- **Структурный шаг группы.** `arrange.group` и `arrange.ungroup` хранят
  образ всего поддерева **с обеих сторон**: группа присутствует (модель в JSON
  вместе с детьми, ключи прямых детей, позиция на верхнем уровне и анимации,
  которые называют её или потомков) либо отсутствует (полные образы бывших
  участников на верхнем уровне с геометрией до группировки или после
  разгруппировки). Undo и redo — одна структурная операция
  `shape_restore{items, remove}`: она сначала убирает фигуры другой стороны
  (`remove`), затем восстанавливает образы этой. Движок удаляет без потери
  анимаций, проверяет и десериализует все образы до первой записи, поэтому шаг
  атомарен; `same_state` сравнивает содержимое присутствующей группы или
  каждого отсутствующего участника, а не позицию. `regroup` по-прежнему
  отключён в collab (§4.4).
- Redo симметричен; лимит 200 шагов / 24 ч на пользователя (ADR-0010).
- `regroup` в collab отключён (см. §4.4).
- Offline: очередь допускается только для merge-операций; `structural` ждёт
  соединения. Долгий разрыв → `resync` и сброс очереди.

## 7. Роли и права (ADR-0008)

- JWT в `hello` (не в URL, не в логах), claims `{sub, doc, role, sid, exp,
  ver}`. Сервер проверяет подпись, `exp`, `doc`, `role` до обработки `op`.
- `viewer`: только `presence`, `resync`, `commit`-запрос не принимается;
  любая `op` → `forbidden`. UI: указатели и команды, меняющие документ,
  отключены (те же `enabled`-проверки, но с серверной гарантией).
- `editor`: все операции, кроме закрытия сессии/смены ролей.
- `owner`: всё + `session.close`, смена ролей, принудительный commit.
- Lease на документ: один writer-lease на сессию (owner/editor), продление
  `ping`; второй owner получает `lease`-конфликт.
- Дополнительно проверяется модель: `Shape.locked` (`model/src/lib.rs:346`)
  уважается на сервере, как и в UI; `hidden` слайды редактируемы.
- Отзыв: разрыв по `sid`; клиент получает `error{code:"auth"}` и уходит в
  read-only до переподключения.
- Автор комментария/заметки — из `sub`, а не из операции
  (`Comment.author`, `model/src/lib.rs:601-613`).

## 8. Commit и версии (ADR-0009)

- Собирает **сервер**: база+журнал → модель → `deckcraft_pptx::export_as(p,
  "pptx")` → `.pptx`. Клиент не коммитит: его preview не авторитетен, а writer
  перенумеровывает `sldId`/`cNvPr` (ADR-0009).
- Ответ: `{bytes|blobRef, sha256, version, fileVersion, warnings[]}`.
- `warnings[]` — **список того, что не сохранится**, а не булев флаг. Для
  DeckCraft вычисляется по модели:
  - медиа с опциями воспроизведения, которые writer не пишет (#74
    `docs/gaps.md`);
  - SmartArt, импортированный как готовая графика (`Diagram.imported`): правка
    текста в его фигурах регенерирует диаграмму;
  - `ShapeKind::Opaque` (OLE, SmartArt без fallback) — сохраняется как XML,
    но не редактируется;
  - 3-D модели (`Model3d`) — сохраняются, не рисуются;
  - SVG-иконки — показывается PNG-fallback.
  Предупреждения перечисляют слайд/фигуру, а не только счётчик.
- `409`: сравниваем с `baseFileETag`, который сервер запомнил при открытии
  сессии, и с etag собственной предыдущей записи этой сессии. Иначе повторный
  commit даёт ложный конфликт (ревью commit/pdfcraft).
- Публикация — server-to-server: сервер POST'ит
  `{fileId, name?, bytes(base64), sha256, version, expectedVersion?}` на
  callback-URL кабинета (`INTEGRATION.md` §5.2) и ждёт `{version, etag}`;
  `409` кабинета — тот же конфликт, вызывающий получает
  `rejected{code:"conflict"}`. Финальный файл никогда не несёт клиент, поэтому
  закрытая вкладка не теряет сохранение. Кабинет может инициировать commit сам:
  `POST /v1/sessions/{sessionId}/commit` с service token; без callback байты
  возвращаются в ответе.
- Принятый `etag` записывается в сессию и в `meta.json` (рестарт не теряет
  версию) и становится `expectedFileVersion` следующего commit.
- Commit инициирует любой writer-клиент — desktop Save, страница через host bridge
  или кабинет через service token: один commit в полёте, повторный Save — тот же
  запрос, а не вторая версия файла; viewer получает отказ до отправки.
- Идемпотентность: повторный commit с той же `(doc, version)` возвращает тот же
  результат.
- Приёмка: файл открывается в PowerPoint/LibreOffice без repair; части,
  которые модель не понимает, совпадают с исходными (корпусные тесты
  `crates/pptx/tests/it/corpus*.rs`).

## 9. Сервер

- **Крейты.** `craft-collab-server` (общий control plane, ADR-0007) +
  `deckcraft-collab-adapter` (библиотека: модель, allowlist, нормализация,
  дельта, снапшот, commit). Адаптер статически линкуется в сервер; отдельного
  бинаря у DeckCraft нет.
- **Зависимости** (проходят licence allowlist: MIT/Apache-2.0/ISC):
  `tokio`, `tokio-tungstenite`, `rustls`, `serde`, `serde_json`, `tracing`,
  `prometheus`-совместимый экспортёр (или собственный `/metrics` без
  зависимости). Существующие `image`, `zip`, `quick-xml` уже в workspace.
- **Модель исполнения:** один воркер на документ (актор), команды
  сериализуются; паника в адаптере → документ `degraded`, процесс живёт
  (house rules «never crash»); `guard` движка уже ловит панику команды
  (`engine/src/guard.rs`).
- **Конфиг:** лимиты документа (медиа ≤ 4 GiB и ≤ 100 000 объектов на файл —
  как в `crates/format/src/lib.rs:29-31`, манифест ≤ 256 MiB; число слайдов —
  параметр сервера, по умолчанию 2000), участники ≤ 16, операций/с, размер
  снапшота, TTL сессии, частота снапшотов, путь хранилища.
- **Healthcheck** `GET /healthz` (жив, версия, число документов),
  `/metrics` (версия, операции/с, размер журнала, время применения p50/p95,
  время commit, ошибки по кодам).
- **Хранение:** `<doc>/base-<version>.deckcraft`, `journal-<from>-<to>.jsonl`,
  `media/<sha256>`, `meta.json` (карта ключей, etag, роли, TTL). Запись
  атомарная (tmp+rename), журнал под flock.
- **Восстановление после рестарта:** последняя целая база + реплей хвоста;
  частично записанный снапшот отбрасывается (хранится 2).
- **Логи:** `doc`, `version`, `opId`, `actorId`, `cmd`, длительность; **без**
  содержимого слайдов, без текста, без байтов медиа, без JWT.

## 10. Клиент

- **Feature flag:** `collab` (env `DECKCRAFT_COLLAB=1` / настройка / query
  `?collab=1` в web-хосте), по умолчанию **выключен**. Выключенный флаг
  оставляет текущий код нетронутым: ни transport, ни новых путей применения.
- **Новый крейт** `crates/collab` (транспорт + клиентская модель сессии),
  чтобы `engine` не тянул сеть: `engine` получает только
  `Session::apply_remote(op)` и `Session::local_op_from_command(...)`.
- **Интеграция с `Session`:**
  - перехват намерения: UI/CLI-команды при включённом флаге нормализуются в
    `op` и идут в `collab` (тонкий слой; `CommandSpec.enabled` продолжает
    работать локально);
  - `apply_remote` — исполнение чужой операции без `push_undo` и без записи в
    пользовательский `journal`;
  - источник истины для отрисовки — локальная модель после применённых
    операций; preview помечается и снимается при `applied`.
- **UI:** presence-слой на canvas (рамки выделения, каретка с цветом и меткой
  имени), список участников с ролями, индикатор `synced|syncing|offline|
  error`, баннер `warnings[]` после commit.
- **Viewer:** команды, меняющие документ, отключены в UI (не только на
  сервере); показ слайдов и presenter view остаются локальными и работают.
- **WASM:** WebSocket через браузерный API, загрузка медиа — `fetch PUT`;
  bytes документа приходят из iframe-хоста, как сейчас
  (`apps/deckcraft-web/src/main.rs:1-14`).

Реализация UI-слоя — `crates/ui-egui/src/collab.rs` (`CollabUi`, индикатор в
статус-баре, панель «Participants», разметка presence на canvas, баннер
`warnings[]`). Флаг читается в `apps/deckcraft/src/main.rs` (`DECKCRAFT_COLLAB`)
и `apps/deckcraft-web/src/web.rs` (`?collab=1`); по умолчанию выключен. Запрет
для viewer — `Session::set_read_only` + `CommandSpec::changes_document`:
отклоняются команды, меняющие документ, а навигация, выделение, копирование,
сохранение и `apply_remote` работают. Роли других участников presence не
несёт, поэтому до отдельного сообщения списка участников они показываются как
«Participant».

## 12. Безопасность

- JWT только в `hello`; токен не попадает в URL, логи, метрики и шину.
- Origin allowlist для web-хоста (same-origin iframe кабинета); desktop —
  pin по `doc`+`role`.
- Лимиты: размер сообщения, число соединений, операции/с, размер документа,
  время применения (таймаут → `rejected{retryable}` и документ `degraded`).
- Права приложения: `Shape.locked`, viewer-режим, защита от OLE/макросов
  (они и так не исполняются).
- Логи без содержимого: `cmd`, адреса-ключи, длительности; текст, байты медиа,
  имена файлов пользователя — не пишем.
- Медиа: приём только по allowlist `content_type`, проверка размера и
  `sha256`; файлы не исполняются, не распаковываются.
- Никаких секретов в репозитории; конфиг сервера — из окружения.

## 13. Открытые вопросы

1. **Канал медиа:** решено — отдельный `PUT /v1/sessions/{id}/media/{sha256}` и
   `GET /media/{sha256}`, чанки по WS не нужны. Реализовано для картинок,
   видео и аудио (раздельные allowlist и бюджеты, §4.1); TLS-клиент медиа для
   `wss://` добавлен в том же срезе.
2. **Форма `delta`:** список изменённых `(slideKey, shapeKey, fields[])` или
   значения полей целиком? Второе дороже, но проще применять.
3. **`format.*` на множестве фигур:** решено для v1 — N операций по одной
   фигуре (§3.2.1); групповая атомарность и один шаг undo на N фигур — позже
   (для undo fill/line шага группы merge-payload уже есть, §6).
4. **Undo структурных операций:** в v1 отменяются Merge-операции одного
   объекта (`shape.move`, `shape.setBounds`, текст, `shape.fill`, `shape.line`,
   `format.*`), шаг `arrange.align`/`arrange.distribute` (образ `xfrm` на
   каждую сдвинутую фигуру, одна `shapes_set_bounds`, §6), fill/outline шага
   **группы** (образ на каждого участника, один `shape_fields`, §6),
   слайдовые structural-шаги (`slide.delete`, `slide.new`,
   `slide.duplicate` — полный образ слайда, `slide_restore`/`slide_delete`) и
   шаги **фигур**: `shape.insert`, `insert.picture`/`insert.video`/`insert.audio`
   и `edit.delete` (полный образ фигуры с z-order и анимациями,
   `shape_restore`/`shape_delete`, §6), а также `arrange.group`/`arrange.ungroup`
   (образ всего поддерева с обеих сторон, одна операция `shape_restore` с
   `remove`, §6), `transition.set` (полный образ перехода: эффект, опция,
   длительность, тайминги, звук и сохранённый XML, `slide_transition`, §3.2.1)
   шаги анимации (`animation.add`/`animation.remove`: полный список шагов
   фигуры, `shape_animations`, §3.2.1; `animation.set`/`animation.timing`/
   `animation.move`/`animation.options`/`animation.clear`/`animation.painterApply`:
   полная последовательность слайда, `slide_animations`,
   §3.2.1), текст заметок слайда (`notes_set`,
   `notes_insert`, `notes_delete`: адрес — слайд, образ шага — всё тело
   заметок, §3.2.1) и `format.*` по одной ячейке таблицы, по N ячейкам одной
   операции и по диапазону ранов/каретке
   (`format_set` с `addresses`, образ шага — тело каждой ячейки или фигуры,
   `cell_text`/`cells_text`/`shape_field`, §3.2.1, §6).
   Остаток табличной поверхности — стиль, опции стиля, заливка ячеек, merge/split и
   размеры столбцов и строк — идёт теми же итоговыми значениями
   (`table_style`, `table_options`, `table_cell_fill`, `table_merge`, `table_split`,
   `table_column_width`, `table_row_height`; образ шага undo — вся таблица,
   §3.2.1). SmartArt-график теперь тоже совместный: `smart_art_set` с целым
   итоговым `Diagram` (контур, layout, style, colors), образ шага — вся группа
   (`shape_field{field: smartArt}`). Диаграммы тоже совместные: `chart_set` и
   `chart_insert` с целым `Chart`, образ шага — вся фигура чарта
   (`shape_field{field: chart}`). SmartArt теперь вставляется тем же правилом:
   `smart_art_insert` с целым `Diagram` (нормализатор считает его движковым
   `smartart::insert_plan`) и итоговым боксом, образ шага undo — вся
   вставленная фигура (undo — `shape_delete`, redo — `shape_restore`); конверсии
   SmartArt (`smart_art_from_text`, `smart_art_to_text`, `smart_art_to_shapes`)
   считаются движковыми `from_text_plan`/`to_text_plan`/`to_shapes_plan`,
   проверяются до первой записи и заменяют исходную фигуру одним структурным
   шагом, образ undo — вся исходная фигура; запрос
   `smartArt.nodes` отвечает сервер (`query`/`query_result`, вне version и
   журнала, viewer тоже может). Картинка в узле тоже совместная:
   `smart_art_picture` несёт дайджест объекта канала и итоговое место, движок
   проверяет цель, узел, allowlist/бюджет картинки, место и неизменность layout
   до первой записи, а образ undo — вся группа (`shape_field{field: smartArt}`).
   Камера 3-D модели тоже совместная: `model3d_camera` несёт всю итоговую
   камеру (или `null`), движок проверяет её до первой записи, а образ undo —
   вся фигура модели (`shape_field{field: model3d}`). Сцена модели
   (`model3d_scene`) — тот же принцип: один источник света и окружение как
   одно итоговое значение (или `null`), проверка до первой записи, образ undo —
   вся фигура модели.
   Открыто: сохранённые части чарта сверх лимита значения и относительные
   эффекты.
5. **Presence во время показа:** показывать ли курсоры других в presenter view
   (сейчас — нет).
6. **Commit при выходе последнего участника**, если он viewer: коммитить
   автоматически или ждать owner (ADR-0009 §Открытые вопросы).
7. **Лимит шага undo** для DeckCraft: 200 шагов / 24 ч (ADR-0010) при 5
   участниках — считать ли бюджет на актора или на документ.

## 14. План поставки

Все PR — в `main` через PR, без изменений CI, фича за флагом.

1. **PR 1: протокол, адаптер и путь применения без undo.**
   `crates/collab-proto` (serde-типы конверта), `deckcraft-collab`
   (нормализация операций по allowlist, `delta`, карта ключей, надгробия,
   перестановки через якорь), `Session::apply_remote` мимо `push_undo`,
   headless-тесты 2 клиентов на модель. Сеть не нужна.
2. **PR 2: per-user undo.** Инверсии на снимках `Arc`, `undo-conflict`,
   отключение `regroup` в collab, лимит шагов; тесты 14–15.
3. **PR 3: транспорт и сервер.** `crates/collab` (WS-клиент, reconnect,
   `resync`), общий `craft-collab-server` + адаптер, снапшоты, дедуп,
   healthcheck/metrics; тесты 11–13, 19.
4. **PR 4: UI.** presence-слой, список участников, индикатор синхронизации,
   viewer-блокировка, баннер `warnings[]`; kittest только на слой.
5. **PR 5: commit.** Серверная сборка `.pptx`, `warnings[]`, `409`,
   идемпотентность; тесты 16–18; прогон корпусных тестов `crates/pptx`.
6. **PR 6 (по готовности):** документация (`docs/collab/`), метрики/perf,
   soak-тест collab-сессии.

Что **не** входит ни в один PR: аккаунты, совместный показ, офлайн-правки,
CRDT, макросы/legacy-форматы.

Пункты 1–5 плана закрыты в ветках `collab/pr1`–`collab/pr10`: протокол и

`shape.insert` и медиа-канал (операция несёт `sha256`, байты идут через
`PUT/GET /media/{sha256}`, объекты переживают рестарт). На `collab/pr10` сверх
`7fe75711`: видео и аудио в медиа-канале (раздельные allowlist и бюджеты),
TLS HTTP-клиент для `wss://`, вертикальные срезы `shape.fill`, `shape.line`,
`format.*` по явной фигуре и `slide.duplicate` (§3.2.1). Сверх этого — undo
fill/line/`format.*` из точного образа значения, undo шага группы (образ на
каждого участника, один `shape_fields`), слайдовый structural undo
(`slide.delete`/`slide.new`/`slide.duplicate` через полный образ слайда и
`slide_restore`) и structural undo фигур (`shape.insert`, `insert.picture`,
`insert.video`/`insert.audio`, `edit.delete` через полный образ фигуры с
z-order, анимациями и триггерами, `shape_restore`/`shape_delete`), undo
`arrange.group`/`arrange.ungroup` (образ всего поддерева с обеих сторон, одна
операция `shape_restore{items, remove}`), срез `transition.set` (весь переход
на проводе как значение модели, undo из полного образа перехода,
`slide_transition`), шаги анимации фигуры (`shape_animations`, undo из полного
списка) и всей последовательности слайда (`slide_animations`, undo из полного
упорядоченного списка для `animation.set`/`timing`/`move`/`options`/`clear`/
`painterApply`) и текст заметок слайда (`notes_set`/`notes_insert`/`notes_delete`:
адрес — слайд, undo из полного тела заметок), а на `collab/pr11` — текст
ячеек таблицы и структурные правки строк/столбцов, шаги анимации, текст
заметок, `format.*` по диапазону ранов/каретке и по N ячейкам одной таблицы
(`format_set` с `addresses`: смещения в символах по телу или каретка,
перебазирование по журналу, undo из целого тела каждой адресованной фигуры или
ячейки, `cells_text` для N ячеек), а затем остаток табличной поверхности
(стиль, опции стиля, заливка ячеек явным списком, merge/split и ширины
столбцов/высоты строк — `table_style`, `table_options`, `table_cell_fill`,
`table_merge`, `table_split`,
`table_column_width`, `table_row_height`; образ шага undo — вся таблица,
слияние накрывшее адресованную ячейку отправляет отложенную операцию в
`stale`), а затем SmartArt: `smart_art_set` с целым итоговым `Diagram`
(контур, layout, style, colors; нормализатор считает его движковым
`smartArt::plan`), образ шага undo — вся группа (`shape_field{field: smartArt}`), а затем диаграммы: `chart_set` и `chart_insert` с целым `Chart` (нормализатор считает значение движковым `chart::plan`), образ шага undo — вся фигура чарта (`shape_field{field: chart}`), а затем вставка SmartArt (`smart_art_insert` с целым `Diagram` от движкового `smartart::insert_plan` и итоговым боксом; образ шага undo — вся вставленная фигура, undo `shape_delete`, redo `shape_restore`), конверсии SmartArt (`smart_art_from_text`/`smart_art_to_text`/`smart_art_to_shapes` с целым результатом движковых `from_text_plan`/`to_text_plan`/`to_shapes_plan`, проверка до первой записи и вся исходная фигура как образ undo) и серверный запрос `smartArt.nodes` (`query`/`query_result` по ключам сессии, без version и журнала), а затем картинка в узле SmartArt (`smart_art_picture`: дайджест и имя объекта существующего медиа-канала и итоговое место — crop и alpha; движковая `smartArt.setPicture` проверяет верхнеуровневую группу, узел, allowlist и бюджет картинки, конечность и положительную площадь места и неизменность layout до первой записи и ставит байты тем же `add_media`, что и вставка картинки; место хранится в модели и пишется как `a:srcRect`; образ undo — вся группа `shape_field{field: smartArt}`). На `collab/pr11` добавлены документные шрифты:
`font.create`/`font.set`/`font.remove` (§3.2, значение презентации),
`font_restore` как образ шага undo, шрифтовые лица в медиа-канале
(собственный allowlist по sfnt-подписи и бюджет 32 объекта / 64 MiB) и
`MediaType::Font`; затем 3-D модели в медиа-канале: `MediaType::Model` по
подписи `glTF` версии 2, отдельный бюджет (16 объектов / 128 МиБ) и
`insert.model3d`, который рисует постер или заглушку; камера модели —
`model3d_camera` с итоговыми `position`/`target`/`up`/`fov` (или `null`),
проверкой до первой записи и всей фигурой модели как образом undo
(`shape_field{field: model3d}`), запись камеры в slide-часть как `am3d:camera`; затем
сцена модели — `model3d_scene` с одним источником света и окружением как целым
итоговым значением (или `null`), проверкой до первой записи и той же всей фигурой
модели как образом undo, запись сцены в slide-часть как `am3d:scene`. Сверх этого —
публикация commit в кабинет: `POST /v1/sessions/{id}/commit` (service token)
строит `.pptx`, сервер сам отправляет его на callback кабинета
(`{fileId, name?, bytes, sha256, version, expectedVersion?}` → `{version, etag}`),
`409` кабинета отдаётся вызывающему, исходная версия в кабинете не
перезаписывается, `etag` переживает рестарт. Браузерная сессия
(`crates/collab-web`, ADR-0016 §3): сообщение `deckcraft:session` открывает
сессию, протокол идёт по `WebSocket` страницы, обратно — `session-state` и
`presence`, Save в живой сессии просит кабинет о `commit`, ответ
`committed` фиксирует версию и `etag`; медиа — `fetch` с токеном сессии,
кадр ждёт свои байты. Тесты, точные коммиты,
матрица приёмки `TASK.md` и список незакрытых блокеров (endpoint кабинета,
CORS, оптимистичный preview, base-transfer, PR) — `docs/collab/STATUS.md`; эксплуатация — `docs/collab/production.md`;
описание PR — `docs/collab/pr10.md`.

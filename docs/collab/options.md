# Options: протокол совместного редактирования DeckCraft

> Артефакт Phase 0, пара к `study.md`. Три варианта различаются **механизмом
> сходимости**, а не настройками. Рекомендация — в §4; она же уходит в шину
> как `proposal` в `protocol/op-unit`.

- Проект: `deckcraft`
- Upstream-коммит: `159ed07eb3f0522a5dc97d7cf1858242a6638659`
- Автор: `deckcraft/envoy`
- Опирается на: `docs/collab/study.md` (ссылки `файл:строка` там же)

## 0. Общие рамки (не обсуждаются вариантами)

Из `TASK.md`, `INTEGRATION.md` и `AGENDA.md` одинаково для всех трёх вариантов:

- authoritative server, JWT в первом WS-сообщении, права проверяются на
  сервере, viewer не пишет;
- фича за флагом, одиночный режим — по умолчанию и без изменений;
- не отправлять весь документ на нажатие: операции + снапшоты + compaction;
- `.pptx` не ломается, немоделируемое (`Opaque`, `raw_ext`, `kept_parts`)
  сохраняется как раньше;
- commit отдаёт готовый файл кабинету, внешнее изменение → `409`;
- медиа — по идентификатору/хэшу, байты один раз, не в операциях
  (в модели байты и так вне JSON: `MediaItem.data` — `serde(skip)`);
- presence — отдельный, нежурналируемый поток;
- один транспорт и конверт для пяти приложений.

Различия ниже — только в том, **как достигается сходимость** и что летит по
проводу.

## 1. Вариант A — нормализованная операция + трансформация (OT)

**Механизм.** `op` = семантическая команда с **явными адресами** (`slideId`,
путь к фигуре, для текста — `(shapeId, cell?, paragraph, char)`), без чтения
`Selection`. Сервер задаёт тотальный порядок (`version`). Клиент применяет
локально оптимистично; получив чужую операцию с меньшей версией, **трансформирует**
свои непринятые операции против неё по матрице трансформаций и повторно
применяет.

```text
op C→S { opId, baseVersion, kind:"shape.move", target:{slide,shape},
         set:{x,y}, clientSeq }
ack S→C { opId, version }
op  S→C { opId, version, author, kind, target, set }   // чужие, в порядке версий
```

**Что нужно построить.**

- Таблица трансформаций для каждой пары конфликтующих видов: вставка/удаление
  текста в одном абзаце, вставка/удаление/перестановка слайдов, `z-order`
  внутри одного списка сиблингов, move/resize одной фигуры.
- Правило «выводимое состояние не пересылается»: рамка группы
  (`refit_groups`), маршрут коннектора (`connect::reroute`), autofit
  пересчитываются на каждой реплике из намерения.
- Отдельный путь применения без `push_undo` (`Session::execute` сейчас пушит
  undo автоматически, `engine/src/lib.rs:680-697`), иначе чужие правки попадут
  в локальную историю.

**Плюсы.**

- Минимальный трафик, «один `op` = одно нажатие».
- Детерминированный серверный порядок, простая идемпотентность по `opId`.
- Привычная модель для текста: `model/src/edit.rs` уже позиционный
  (`insert/delete/format` по `(paragraph, char)`), трансформация — классическая
  OT-арифметика на целых.

**Минусы.**

- Матрица трансформаций для 329 команд нереальна; придётся вводить свой узкий
  набор видов операций (`shape.move`, `shape.xfrm.set`, `shape.insert`,
  `shape.delete`, `shape.reorder`, `text.insert`, `text.delete`,
  `text.format`, `table.cell…`, `slide.*`, `anim.*`), то есть **второй**
  словарь команд рядом с `CommandSpec`.
- Каждая новая фича UI требует новой пары трансформаций — риск тихой
  расходимости там, где пару забыли. Для таблиц, диаграмм и SmartArt
  трансформации придётся объявить «конфликтом», то есть частично отказаться от
  автоматики.
- Ошибка в трансформации ломает сходимость незаметно: тесты нужны на каждую
  пару.

## 2. Вариант B — журнал команд, серверный порядок, rebase откатом/повтором

**Механизм.** `op` = **нормализованная команда** (id команды + явные адреса и
параметры, без `Selection`). Клиент применяет её оптимистично. Пришла чужая
операция — клиент **откатывается к последнему подтверждённому `Arc`-снимку**
документа и **повторно выполняет** все свои непринятые операции поверх нового
состояния, пере-проверяя `enabled`/предусловия. Никакой матрицы трансформаций:
сходимость достигается тем, что все реплики исполняют один и тот же
детерминированный код над одним и тем же состоянием и порядком.

```text
op C→S { opId, baseVersion, clientSeq, cmd:"shape.move", addr:{slide,shape},
         args:{x,y} }
ack S→C { opId, version }              // принято в этом порядке
reject S→C { opId, version, code }     // предусловие не выполнено — op снят
op  S→C { opId, version, author, cmd, addr, args }   // чужие, в порядке версий
```

**Почему это дёшево именно в DeckCraft.**

- Откат к снимку — замена `Arc<Presentation>`: undo-история уже так устроена
  (`HistoryEntry.doc: Arc<Presentation>`, `engine/src/lib.rs:167-173`), а
  `Session::edit` клонирует `Vec<Arc<Slide>>` и `Arc::make_mut` только
  затронутый слайд (`:727-738`). Значит `rollback + N × replay` стоит
  O(N × один слайд), а не O(N × колода), и не копирует медиа (там `Arc<Vec<u8>>`).
- «Выводимое» состояние (`refit_groups`, `connect::reroute`, autofit текста)
  пересчитывается тем же кодом на каждой реплике. Это прямо снимает главный
  риск проекта: при одновременном перемещении фигур одной группы каждая
  реплика пересчитывает рамку группы из детей, а не применяет чужую готовую
  рамку (`cmd/arrange.rs:238-315`).
- Журнал команд уже есть (`Session.journal`, `:692-697`) — как прообраз,
  с оговорками (без версий и opId, включает локальные команды).
- Сервер хранит снапшот в нативном формате: `crates/format` пишет
  `presentation.json` без байтов медиа + `media/<id>` + `chart-parts/<index>`
  (`crates/format/src/lib.rs:1-5,73-100`) — готовый формат для снапшота и
  отдельного медиа-хранилища по `MediaId`.

**Цена и ограничения.**

- Нужен **whitelist реплицируемых команд**: те, что не читают `Selection`, не
  ходят в файловую систему, не зависят от времени и не используют локальные
  предпочтения (`Session.prefs`: smart quotes, `mac_keys`). `text.insert` сейчас
  берёт каретку из `selection.text` (`cmd/text/editing.rs:75-100`) — значит
  операция обязана нести явную позицию и явные `props`.
- Rebase повторяет работу: при плотном потоке чужих операций N непринятых
  локальных команд переигрываются на каждую чужую. Нужны: батчинг (сервер
  отдаёт пачку версий), ограничение «не более N непринятых», пауза набора
  (coalescing по 150–300 мс), отказ от replay для дорогих команд.
- Позиционные структуры всё равно требуют **узкой** трансформации: если двое
  печатают в одном абзаце, повторное выполнение `text.insert {at:(p,c)}`
  вставит символ в неверное место. Здесь нужен один маленький transform
  (сдвиг `char` при чужой вставке/удалении в том же абзаце) либо переход на
  per-paragraph последовательность с якорями. Это единственная «OT-часть».
- `regroup` опирается на локальную историю undo (`cmd/arrange.rs:373-386`) —
  в совместном режиме его надо либо запретить, либо сделать операцией с
  явными `ids`.
- Запоздавшие операции: сервер обязан отклонять `op` по адресу, которого уже
  нет (надгробия), иначе повторное применение воскресит фигуру.

**Плюсы.**

- Один словарь: операции — это подмножество существующих команд, а не второй
  API. UI, CLI и collab идут через один код.
- Нет матрицы трансформаций на 329 команд; трансформация нужна только у текста.
- Выводимое состояние пересчитывается локально — сходимость следует из
  детерминизма, а не из математики OT.
- Per-user undo ложится естественно: локальная история — снимки `Arc`; чужие
  операции применяются не через `execute`, а через отдельный путь, поэтому в
  неё не попадают; undo пользователя = вернуть свой `Arc` и переиграть свои
  непринятые.

**Минусы.**

- Rebase — самая дорогая операция по CPU, и её цена зависит от дисциплины
  «непринятых»; нужны лимиты и метрики.
- Требует явных адресов и нормализации для команд, которые сейчас читают
  `Selection` (работа на этапе RFC, не на этапе протокола).
- Offline-очередь длиной в сотни операций переигрывать дорого — нужен
  практический предел и «полная перезагрузка снапшотом» после долгого офлайна.

## 3. Вариант C — CRDT-lite по структурам модели

**Механизм.** Порядок слайдов, `z-order` и символы текста — последовательности
RGA/Logoot; скалярные свойства фигур — LWW-регистры с гибридными часами;
группа — LWW на `group/ungroup` плюс выводимая рамка. Сервер — ретранслятор +
снапшот + авторизация, арбитража порядка нет.

**Плюсы.**

- Сходимость без арбитража, offline «бесплатно», нет откатов и replay.
- Хорошо изученные реализации на Rust существуют.

**Минусы и почему для DeckCraft плохо.**

- Модель — не CRDT-структуры: `Vec<Arc<Slide>>` и `Vec<Shape>` с
  `Arc::make_mut` (`model/src/lib.rs:974-1015`, `:617-640`), а не
  идентифицируемые узлы с часами. Нужен параллельный «CRDT-вид» и постоянная
  проекция туда-обратно; расхождение вида и модели станет новым классом багов.
- Все производные величины (`refit_groups`, `connect::reroute`, autofit,
  разрешение placeholder'ов slide→layout→master→theme,
  `model/src/resolve.rs`) — не данные, а функции. Их нельзя «слить»
  регистром; их всё равно надо пересчитывать, то есть сервер нужен.
- Таблицы (индексы строк/столбцов, объединённые ячейки), диаграммы
  (`Chart.kept` XML), анимации (плоский список по `ShapeId`) и `Opaque`-XML
  в CRDT не ложатся; для них всё равно нужен авторитетный порядок — то есть
  получается гибрид C+B с двумя механизмами.
- Требование «не тащить тяжёлый CRDT-стек» (`AGENDA.md`, критерий 6) прямо
  противоречит выбранному механизму.
- Commit всё равно перенумеровывает слайды и фигуры (`pptx/src/write.rs:1112`,
  `write/shapes.rs:20-40`), права и `409` — на сервере; CRDT не даёт здесь
  ничего.

## 4. Сравнение и рекомендация

| Критерий (`AGENDA.md` §«Критерии оценки») | A (OT) | B (журнал + rebase) | C (CRDT-lite) |
|---|---|---|---|
| 1. Round-trip `.pptx` не ломается | да | да | да (commit всё равно на сервере) |
| 2. 2–5 участников, 100+ слайдов | да | да | да |
| 3. Нет полного документа на нажатие | да | да | да |
| 4. Per-user undo | да, но сложно отделить | **естественно** (снимки `Arc`, отдельный путь применения) | да, через undo-менеджер поверх CRDT |
| 5. Headless-тесты 2–3 клиента | да, но каждую пару трансформаций | **да**: soak-инфраструктура (`engine/src/soak_tests.rs`) гоняет команды без GUI | да, но нужен CRDT-харнесс |
| 6. Разумный объём на Rust/WASM | средний: матрица трансформаций | **средний**: whitelist + rebase + 1 transform для текста | высокий: CRDT-стек + проекция модели |
| 7. Один конверт на 5 приложений | да | **да** | да |
| Проектные исключения (оценка) | текст, z-order, слайды, таблицы, диаграммы → много | текст (узкая трансформация), `regroup`, «нечистые» команды | таблицы, диаграммы, анимации, `Opaque`, все производные величины |
| Главный риск DeckCraft (группы + z-order) | требует трансформаций для `reorder` и xfrm | **снимается**: производные пересчитываются локально | частично: рамка группы выводима, но порядок и права всё равно на сервере |

**Рекомендация: B.**

Обоснование фактами репозитория:

1. Единица правки уже существует и детерминирована — `Session::execute` над
   `Arc<Presentation>` (`engine/src/lib.rs:636-699`); второй словарь операций
   (A) или параллельная модель (C) дублируют то, что уже поддерживается.
2. Откат к снимку в этой архитектуре — операция над указателем
   (`HistoryEntry.doc`, `:167-173`), поэтому «повторить непринятые» дешевле,
   чем в приложениях, где снимок — копия документа. Это делает rebase
   практичным именно здесь.
3. Производное состояние (рамка группы, маршрут коннектора, autofit)
   пересчитывается кодом (`cmd/arrange.rs:238-315`) — значит «пересылать
   намерение, а не результат» не требует новых механизмов и прямо закрывает
   риск «z-order и группы ломаются».
4. Позиционная часть, для которой rebase недостаточно, узкая и уже
   изолирована: `model/src/edit.rs` даёт чистые `insert/delete/format` по
   `(paragraph, char)`. Одна маленькая функция трансформации вместо матрицы.
5. Требование «не тащить тяжёлый CRDT-стек» и «реализуемо в Rust/WASM»
   выполняется без новых тяжёлых зависимостей; сетевой код пишется с нуля
   (в проекте нет ни одной сетевой зависимости).

Что вариант B **не** решает и должно попасть в RFC как ограничение:

- очень длинный offline (> ~50–100 операций) → перезагрузка снапшотом, а не
  replay;
- команды, читающие локальное состояние (`Selection`, `prefs`), не
  реплицируются, пока не нормализованы;
- `regroup` и всё, что опирается на локальную историю, — вне совместного
  режима или переделывается на явные `ids`;
- плотный поток в один абзац требует отдельного решения (узкая трансформация
  или per-paragraph последовательность).

## 5. Как B ложится на десять измерений `AGENDA.md`

| # | Измерение | Ответ варианта B для DeckCraft |
|---|---|---|
| 1 | Единица операции | нормализованная команда: `cmd` + явный адрес (`slideId`, путь фигуры, `(paragraph, char)` для текста) + `args`; не `Selection` |
| 2 | Идентификаторы | session-scoped `(slideKey, shapeKey)`; `slideKey` — UUID, выданный при входе в сессию; `shapeKey` — файловый `cNvPr` при импорте (уникален в слайде), новый UUID для вставленных; надгробия для удалённых; `MediaId` — по хэшу содержимого |
| 3 | Порядок и версии | серверный монотонный `version`; `opId` = `(clientId, clientSeq)`; дедупликация по `opId`; `baseVersion` для ack/reject |
| 4 | Конфликты | серверный порядок + `reject` по невыполненному предусловию + rebase откатом/повтором; last-writer-wins на уровне команды; узкая трансформация позиций в абзаце |
| 5 | Снапшоты | каждые N версий (и по таймеру) — нативный `.deckcraft` (`presentation.json` + `media/<id>`), журнал обрезается до снапшота; восстановление = снапшот + replay хвоста |
| 6 | Presence | отдельный нежурналируемый поток поверх того же WS: `slideKey`, `shapes[]`, `text {anchor, caret}`, `viewport`; троттлинг 5–10 Гц, последнее состояние важнее предыдущих; `Selection` уже содержит ровно эти поля (`engine/src/lib.rs:148-164`) |
| 7 | Топология сервера | общий sync-сервис на пять приложений, приложение — плагин-адаптер (модель + whitelist команд + снапшот-формат); DeckCraft нужен только «команда → модель» |
| 8 | Auth и lease | JWT в первом WS-сообщении (`auth`), claims `sub`, `doc`, `role`, `ver`; одна активная сессия на документ, lease продлевается `ping`; отзыв — `reject` + закрытие; права проверяются на сервере до применения |
| 9 | Commit | собирает сервер из своего состояния: снапшот модели → `deckcraft-pptx` → `.pptx`; версия файла (ETag/хэш) проверяется до commit, расхождение → `409`; клиентский экспорт перенумеровывает IDs (`256 + i`), поэтому commit только серверный |
| 10 | Offline и undo | undo на пользователя: своя история снимков `Arc` + инверсия своих операций; чужие операции идут минуя `push_undo`; offline-очередь с пределом и «перезагрузка снапшотом» после долгого разрыва; reconnect = `auth{lastVersion}` + снапшот/догон |

## 6. Открытые вопросы к шине

1. **Единица операции.** Устраивает ли соседей «команда с явными адресами»
   вместо «нормализованной операции над моделью»? Для WordCraft/GridCraft это
   вопрос их command surface; DeckCraft предлагает именно это.
2. **Трансформация текста.** Один общий узкий transform для текста на все пять
   приложений или у каждого свой? DeckCraft может жить с общим:
   `(paragraph, char)` + сдвиг.
3. **Идентификаторы в файле.** Принимаем ли общее правило «session-scoped
   ключи + надгробия», зная, что `.pptx`/`.docx`/`.xlsx` не хранят стабильных
   id (DeckCraft перенумеровывает слайды при экспорте)?
4. **Снапшот.** Нативный формат приложения (`.deckcraft`, `presentation.json` +
   медиа) или общий конверт? DeckCraft за нативный + общий манифест.
5. **Commit.** Кто владеет сборкой файла: сервер (DeckCraft — да) или клиент
   с последующей загрузкой? Нужно одинаково для пяти проектов.

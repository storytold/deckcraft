# Options: протокол совместного редактирования DeckCraft

> Артефакт Phase 0, пара к `study.md`. Три варианта различаются **механизмом
> сходимости**, а не настройками. Рекомендация — в §4; она же уходит в шину
> как `proposal` в `protocol/op-unit`.
>
> Метки вариантов совпадают с конвенцией соседей (wordcraft, gridcraft):
> **A** — команда как операция, **B** — слой нормализованных примитивов над
> моделью, **C** — CRDT. Это сделано намеренно: иначе голоса по измерению 1
> считались бы по разным шкалам.

- Проект: `deckcraft`
- Upstream-коммит: `159ed07eb3f0522a5dc97d7cf1858242a6638659`
- Автор: `deckcraft/envoy`
- Опирается на: `docs/collab/study.md` (ссылки `файл:строка` там же)

## 0. Общие рамки (не обсуждаются вариантами)

Из `TASK.md`, `INTEGRATION.md` и `AGENDA.md` одинаково для всех трёх вариантов:

- authoritative server, JWT в первом WS-сообщении, права проверяются на
  сервере, viewer не пишет;
- фича за флагом, одиночный режим — по умолчанию и без изменений;
- не отправлять весь документ на нажатие: операции + снапшоты + compaction;
- `.pptx` не ломается, немоделируемое (`Opaque`, `raw_ext`, `kept_parts`)
  сохраняется как раньше;
- commit отдаёт готовый файл кабинету, внешнее изменение → `409`;
- медиа — по идентификатору/хэшу, байты один раз, не в операциях
  (в модели байты и так вне JSON: `MediaItem.data` — `serde(skip)`);
- presence — отдельный, нежурналируемый поток;
- один транспорт и конверт для пяти приложений.

Различия ниже — только в том, **что сервер обязан уметь** и **как достигается
сходимость**.

## 1. Вариант A — команда как операция (+ явные адреса, server order, rebase)

**Механизм.** `op` = **существующая команда** движка (`engine/src/cmd/*`),
но нормализованная: вместо выборки/каретки/активного листа в параметрах
передаются **явные адреса** и итоговые значения. Сервер — единственный
писатель: выполняет ту же команду на своей копии (`Session::execute`) и
рассылает подтверждённую операцию в тотальном порядке (`version`). Клиент
применяет локально оптимистично; пришла чужая операция с меньшей версией —
**откатывается к последнему подтверждённому `Arc`-снимку и повторяет свои
непринятые операции** (rebase), пере-проверяя предусловия. Никакой матрицы
трансформаций: сходимость следует из детерминизма и единого порядка.

```text
op      C→S { opId, baseVersion, clientSeq, cmd:"shape.move",
              addr:{slide,shape}, args:{x,y}, author }
ack     S→C { opId, version }            // принято в этом порядке
reject  S→C { opId, version, code }      // предусловие не выполнено — op снят
op      S→C { opId, version, author, cmd, addr, args }   // чужие, по версиям
```

**Что нужно построить.**

1. «Нормализованный» слой для команд: адрес (`slideKey`, `shapeKey`, для
   текста `(shape, cell?, paragraph, char)`) вместо `Selection`. Сегодня
   `text.insert` берёт каретку из `selection.text`
   (`engine/src/cmd/text/editing.rs:75-100`), `shape.move` берёт выделение
   (`engine/src/cmd/shape.rs:61-66`) — такие команды нельзя слать как есть.
2. Whitelist реплицируемых команд: чистые, без файлового ввода-вывода, без
   времени, без локальных предпочтений (`Session.prefs`: smart quotes,
   `mac_keys`). Остальные — локальные или серверные отдельным типом.
3. Отдельный путь применения чужой операции, минуя `push_undo`: сейчас
   `execute_unguarded` пушит undo для любой `undoable` команды
   (`engine/src/lib.rs:683-691`), иначе чужая правка попадёт в локальную
   историю.
4. Узкая трансформация **только для позиций в абзаце**: повторное выполнение
   `text.insert {at:(p,c)}` после чужой вставки/удаления в том же абзаце
   поставит символ не туда. Это один сдвиг `char`, а не OT по всем структурам.
5. Надгробия: сервер отклоняет `op` по адресу, которого уже нет, иначе
   запоздавшая операция воскресит слайд или фигуру.

**Почему это дёшево именно в DeckCraft.**

- Откат — замена `Arc<Presentation>`: undo уже так устроен
  (`HistoryEntry.doc: Arc<Presentation>`, `engine/src/lib.rs:167-173`), а
  `Session::edit` клонирует `Vec<Arc<Slide>>` и делает `Arc::make_mut` только
  на затронутом слайде (`:727-738`). `rollback + N × replay` стоит
  O(N × один слайд), не O(N × колода), и не копирует байты медиа
  (`Arc<Vec<u8>>`).
- Производное состояние (`refit_groups`, `connect::reroute`, autofit)
  пересчитывается тем же кодом на каждой реплике — значит **не надо
  пересылать результат**. Это прямо снимает главный риск проекта: при
  одновременном перемещении детей одной группы каждая реплика пересчитывает
  рамку группы из детей, а не применяет чужую готовую рамку
  (`engine/src/cmd/arrange.rs:238-315`).
- Журнал команд уже есть (`Session.journal`, `:692-697`) — как прообраз, с
  оговорками: без версий и `opId`, включает локальные и UI-команды.
- Снапшот сервера — нативный формат: `crates/format` пишет
  `presentation.json` (модель без байтов медиа) + `media/<id>` +
  `chart-parts/<index>` (`crates/format/src/lib.rs:1-5,73-100`). Готовый
  формат снапшота и отдельного медиа-хранилища по `MediaId`.

**Плюсы.**

- Один словарь: операции — подмножество существующих команд, а не второй API.
  UI, CLI, MCP и collab идут через один код.
- Нет матрицы трансформаций на 329 команд; трансформация нужна только тексту.
- Выводимое состояние считается локально — сходимость из детерминизма.
- Per-user undo естественен: локальная история — снимки `Arc`; чужие операции
  идут своим путём; undo = вернуть свой снимок и переиграть свои непринятые.

**Минусы.**

- Rebase — самая дорогая операция по CPU, цена зависит от числа непринятых
  операций: нужны батчинг версий, coalescing набора (150–300 мс), лимит
  непринятых и метрики.
- Требует нормализации команд, читающих `Selection` (работа в RFC, не в
  протоколе).
- Долгий offline (сотни операций) переигрывать дорого — нужен предел и
  «перезагрузка снапшотом».
- Приложение обязано иметь headless-путь исполнения команд (у DeckCraft есть:
  `Session` без GUI, soak-тесты).

## 2. Вариант B — слой нормализованных примитивов над моделью (+ OT путей)

**Механизм.** Второй, узкий словарь операций над моделью (≈20–30 примитивов:
`shape.set_xfrm`, `shape.insert`, `shape.delete`, `shape.reorder`,
`text.insert`, `text.delete`, `text.format`, `table.…`, `slide.…`),
реализованный напрямую через модель (`model/src/edit.rs`, `model/src/lib.rs`),
в обход `CommandSpec`. Клиент выводит примитив из своей команды; сервер
транслирует индексные пути (позиции блоков/ячеек/символов) через маленький OT
и рассылает подтверждённые операции.

**Плюсы.**

- Операции мельче и не зависят от UI-контекста.
- Текст ложится идеально: `model/src/edit.rs` уже даёт `insert/delete/format`
  по `(paragraph, char)`.
- Журнал с `author` даёт per-user undo через инверсии примитивов.

**Минусы (почему для DeckCraft это дороже, чем кажется).**

- Примитивы должны воспроизвести **всё**, что делает команда помимо мутации:
  `refit_groups` и `connect::reroute` (`engine/src/lib.rs:727-738`),
  автофит текстового блока (`fit_text_box` в `cmd/text.rs`), пере-привязку
  медиа (`media_refs`), очистку ссылок анимаций (`remap_animations`,
  `cmd/edit.rs:230-237`), ограничения `MAX_GROUP_DEPTH`, `locked`, `NO_ID_SPACE`.
  Это не «обёртка», а вторая модель мутаций, которую надо держать в паритете с
  329 командами.
- Каждый новый примитив требует пары трансформаций с каждым конфликтующим —
  матрица растёт квадратично там, где структуры пересекаются (z-order внутри
  группы × группировка × удаление слайда).
- `regroup` опирается на локальную историю undo (`cmd/arrange.rs:373-386`) —
  в примитивах он не выражается.
- Второй словарь расходится с `CommandSpec.params`, и `deckcraft-cli
  describe`/MCP перестают быть источником правды.

## 3. Вариант C — CRDT-lite по структурам модели

**Механизм.** Порядок слайдов, `z-order` и символы текста — последовательности
RGA/Logoot; скалярные свойства фигур — LWW-регистры с гибридными часами;
группа — LWW на `group/ungroup` плюс выводимая рамка. Сервер — ретранслятор +
снапшот + авторизация; арбитража порядка нет.

**Плюсы.** Сходимость без арбитража, offline «бесплатно», нет откатов и replay.

**Минусы.**

- Модель — не CRDT-структуры: `Vec<Arc<Slide>>` и `Vec<Shape>` с
  `Arc::make_mut` (`model/src/lib.rs:974-1015`, `:617-640`). Нужен параллельный
  «CRDT-вид» и постоянная проекция; расхождение вида и модели — новый класс
  багов.
- Производные величины (`refit_groups`, `connect::reroute`, autofit,
  разрешение placeholder'ов slide→layout→master→theme в `model/src/resolve.rs`)
  — функции, а не данные: их всё равно пересчитывать, то есть сервер нужен.
- Таблицы (индексы строк/столбцов, объединённые ячейки), диаграммы
  (`Chart.kept` XML), анимации (плоский список по `ShapeId`) и `Opaque`-XML
  в CRDT не ложатся — для них всё равно нужен авторитетный порядок, то есть
  гибрид C+A с двумя механизмами.
- «Не тащить тяжёлый CRDT-стек» (`AGENDA.md`, критерий 6) противоречит
  механизму.
- Commit всё равно перенумеровывает слайды и фигуры
  (`pptx/src/write.rs:1112`, `pptx/src/write/shapes.rs:20-40`), права и `409` —
  на сервере; CRDT здесь ничего не даёт.

## 4. Сравнение и рекомендация

| Критерий (`AGENDA.md` §«Критерии оценки») | A (команда) | B (примитивы+OT) | C (CRDT-lite) |
|---|---|---|---|
| 1. Round-trip `.pptx` не ломается | да: мутирует только модель, `Opaque`/`raw_ext` не трогаются | да, если примитивы не теряют `raw_ext`/`kept` | да (commit на сервере) |
| 2. 2–5 участников, 100+ слайдов | да | да | да |
| 3. Нет полного документа на нажатие | да: десятки байт на операцию | да, ещё мельче | да |
| 4. Per-user undo | **естественно**: снимки `Arc` + отдельный путь применения | через инверсии примитивов (писать и тестировать) | через undo-менеджер поверх CRDT |
| 5. Headless-тесты 2–3 клиента | **да**: `Session` без GUI, soak-тесты уже гоняют команды | да, но нужен харнесс на примитивы | да, но нужен CRDT-харнесс |
| 6. Разумный объём на Rust/WASM | **средний**: whitelist + rebase + 1 transform для текста | высокий: паритет второй модели мутаций | высокий: CRDT-стек + проекция модели |
| 7. Один конверт на 5 приложений | **да** | да | да |
| Главный риск DeckCraft (группы + z-order) | **снят**: производные пересчитываются локально из намерения | снят, но `reorder`/группировка требуют трансформаций | частично: порядок и права всё равно на сервере |

**Рекомендация: A.**

Обоснование фактами репозитория:

1. Единица правки уже существует и детерминирована — `Session::execute` над
   `Arc<Presentation>` (`engine/src/lib.rs:636-699`); вариант B добавляет вторую
   модель мутаций, которую надо держать в паритете с 329 командами, включая
   производные пересчёты.
2. Откат к снимку здесь — операция над указателем (`HistoryEntry.doc`,
   `:167-173`), поэтому «повторить непринятые» дешевле, чем в приложениях, где
   снимок — копия документа. Rebase практичен именно в этой архитектуре.
3. Производное состояние (рамка группы, маршрут коннектора, autofit)
   пересчитывается кодом (`cmd/arrange.rs:238-315`) — «пересылать намерение, а
   не результат» не требует новых механизмов и прямо закрывает риск «z-order и
   группы ломаются».
4. Позиционная часть, для которой rebase недостаточно, узкая и уже
   изолирована: `model/src/edit.rs` даёт чистые `insert/delete/format` по
   `(paragraph, char)`. Нужна одна маленькая функция сдвига, а не матрица.
5. Требование «не тащить тяжёлый CRDT-стек» и «реализуемо в Rust/WASM»
   выполняется без новых тяжёлых зависимостей: сетевого кода в проекте нет
   вовсе, транспорт пишется с нуля под native и wasm.

Что вариант A **не** решает и что должно попасть в RFC как ограничение:

- очень длинный offline (> ~50–100 операций) → перезагрузка снапшотом, а не
  replay;
- команды, читающие локальное состояние (`Selection`, `prefs`), не
  реплицируются, пока не нормализованы;
- `regroup` и всё, что опирается на локальную историю, — вне совместного
  режима или переделывается на явные `ids`;
- плотный поток в один абзац требует узкой трансформации позиций (или
  per-paragraph последовательности) — это единственная «OT-часть».

## 5. Как вариант A ложится на десять измерений `AGENDA.md`

| # | Измерение | Ответ для DeckCraft |
|---|---|---|
| 1 | Единица операции | команда как операция: `cmd` + явный адрес (`slideKey`, `shapeKey`, `(paragraph, char)`) + итоговые `args`; сервер исполняет ту же команду |
| 2 | Идентификаторы | session-scoped `(slideKey, shapeKey)`; `slideKey` — UUID при входе в сессию; `shapeKey` — файловый `cNvPr` при импорте (уникален в слайде), новый UUID для вставленных; надгробия для удалённых; `MediaId` — по хэшу содержимого |
| 3 | Порядок и версии | серверный монотонный `version`; `opId = (clientId, clientSeq)`; дедупликация по `opId`; `baseVersion` для ack/reject |
| 4 | Конфликты | серверный порядок + `reject` по невыполненному предусловию + rebase откатом/повтором; last-writer-wins на уровне команды; узкий сдвиг позиций в абзаце; структурные операции (удаление слайда/перестановка) — эксклюзивные |
| 5 | Снапшоты | каждые N версий и по таймеру — нативный `.deckcraft` (`presentation.json` + `media/<id>`); журнал обрезается до снапшота; восстановление = снапшот + replay хвоста |
| 6 | Presence | отдельный нежурналируемый поток поверх того же WS: `slideKey`, `shapes[]`, `text{anchor,caret}`, `viewport`; 5–10 Гц, последнее состояние важнее предыдущих; `Selection` уже содержит ровно эти поля (`engine/src/lib.rs:148-164`) |
| 7 | Топология сервера | один sync-сервис на пять приложений; приложение — адаптер (модель, whitelist команд, формат снапшота, сборка файла); DeckCraft нужен только «команда → модель» |
| 8 | Auth и lease | JWT в первом WS-сообщении (`auth`), claims `sub`, `doc`, `role`, `ver`; одна активная сессия на документ, lease продлевается `ping`; отзыв — `reject` + закрытие; права проверяются до применения |
| 9 | Commit | собирает сервер из своего состояния: снапшот модели → `deckcraft-pptx` → `.pptx`; версия файла (ETag/хэш) проверяется до commit, расхождение → `409`; клиентский экспорт перенумеровывает IDs (`256 + i`), поэтому commit только серверный |
| 10 | Offline и undo | undo на пользователя: своя история снимков `Arc` + переигрывание своих операций; чужие операции минуют `push_undo`; offline-очередь с пределом и «перезагрузка снапшотом» после долгого разрыва; reconnect = `auth{lastVersion}` + снапшот/догон |

## 6. Открытые вопросы к шине

1. **Единица операции.** Согласны ли соседи, что «команда как операция»
   требует **нормализации адресов** (иначе операция нереплицируема)? Для
   DeckCraft это обязательное условие: `text.insert` читает каретку из
   `Selection`.
2. **Трансформация текста.** Один общий узкий сдвиг позиций
   `(paragraph, char)` на все пять приложений или у каждого свой? DeckCraft
   может жить с общим.
3. **Идентификаторы в файле.** Принимаем ли «session-scoped ключи +
   надгробия», зная, что `.pptx`/`.docx`/`.xlsx` не хранят стабильных id
   (DeckCraft перенумеровывает слайды при экспорте)?
4. **Снапшот.** Нативный формат приложения (`.deckcraft`: `presentation.json` +
   медиа) или общий конверт? DeckCraft за нативный + общий манифест.
5. **Commit.** Кто владеет сборкой файла: сервер (DeckCraft — да) или клиент
   с последующей загрузкой? Нужно одинаково для пяти проектов.
6. **Серверная дельта.** GridCraft без неё неполон из-за недетерминизма
   (`NOW/RAND`, Python, precision). Для DeckCraft дельта — оптимизация, не
   необходимость; готовы принять её как общий элемент конверта.

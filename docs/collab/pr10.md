## Title

```text
feat(collab): realtime collaborative editing
```

## Description

### What

Real-time collaboration for DeckCraft presentations: one authoritative session per document,
ordered operations with de-duplication, per-user undo, presence, reconnect, viewer roles and a
server-side `.pptx` commit. The whole feature is behind a flag and is off by default.

### Why

The cabinet needs a browser-capable editor without a server-side OnlyOffice; today DeckCraft is a
single-user editor. Two or more people must be able to edit one deck at the same time without
losing each other's text, and the result must still open as a valid `.pptx`.

### How

- **Model**: authoritative server, one `Hub` per document. The server applies each operation to the
  engine and broadcasts the confirmed command, so every replica runs the same command in the same
  order. No OT/CRDT dependency: operations carry final values, and the few relative edits
  (`text.insert`, `text.delete`) are rebased against the journal tail on the server.
- **Protocol**: WebSocket, JSON envelope `hello/welcome/op/applied/rejected/presence/resync/
  snapshot/commit-result/error/ping`. The token travels in the first frame, never in the URL. The
  actor and role come from the JWT. One server `version` orders everything, `opId` de-duplicates a
  10 000-entry window, structural operations are exclusive at the head, tombstones refuse late
  operations.
- **Identity**: session keys (`slideKey`, `shapeKey`) are derived identically on both sides from
  `fileId` plus the same document walk; new object ids are deterministic on every replica.
- **Storage**: optional `COLLAB_STORE_DIR` keeps a native base plus an append-only journal, flushed
  before apply, with a snapshot every 200 operations and replay through the same `apply` path.
  Without it the server is memory-only.
- **Media**: pictures, audio and video do not travel in operations.
  `PUT /v1/sessions/{id}/media/{sha256}` stores content-addressed bytes (signature allowlist:
  images ≤ 8 MiB with 512 objects / 64 MiB; audio and video ≤ 32 MiB with 32 objects / 192 MiB per
  session) and the operation carries only the digest; every replica fetches it. The desktop HTTP
  client follows the link scheme: `ws://` is plain, `wss://` uses `rustls` with the platform roots.
- **Client**: `CollabDoc` normalises commands to absolute operations and applies the confirmed
  commands; unanswered operations return to the front of the queue on a disconnect and are resent
  with the same `opId`. `WsTransport` reconnects with the same handshake.
- **UI**: flag `DECKCRAFT_COLLAB=1` (web `?collab=1`) shows the status indicator, participants,
  remote selections/carets, commit warnings and the viewer lock. With the flag off nothing changes.
- **Roles and limits**: a viewer's operation is refused by the server and by the engine's read-only
  gate. Message size, operations/second and participants are bounded.
- **Commit**: the server builds the `.pptx` from the authoritative document and returns
  `sha256`, inline bytes and `warnings[]`; a stale `expectedVersion` is a `409` and never
  overwrites an externally changed file.

### Flag and compatibility

- Off by default: no transport, no command normalisation, `Session::is_read_only()` is `false`.
- File format untouched: the writer is the existing `crates/pptx` writer; the native base is the
  existing `.deckcraft` format.
- Existing commands, CLI and MCP are unchanged; a collab room introduces no new required
  configuration for single-user runs.

Covered scenarios:

- two editors converge on shapes, text, slides, groups and order; concurrent text inserts in one
  paragraph keep both texts (server-side rebase);
- duplicate `opId` is applied once; a late operation on a deleted object is refused by the
  tombstone; structural operations do not interleave;
- per-actor undo/redo with `undo-conflict` when someone else touched the object; fill, outline and
  `format.*` steps restore the exact model value they replaced;
- reconnect: unanswered operations are resent with the same `opId`; `resync` replays the tail;
- viewer: server refusal and engine refusal;
- security: invalid/expired token, wrong app/file/session, rate and size limits;
- restart: a room reopens from the base and journal with the same version and document;
- media: rejected uploads (viewer, wrong digest, no token), one object for repeated bytes, a
  picture applied from a reference, and a journal replay that loads the object before the
  operation;
- flag off: single-user behaviour and the engine test suite are unchanged.

### Limits (deliberately out of this PR)

- The v1 command set is collaborative (`shape.move/setBounds`, `text.set/insert/delete`,
  `shape.insert`, `insert.picture/video/audio`, `shape.fill`, `shape.line`, 17 `format.*`
  commands over an explicit shape, `edit.delete`, `slide.new/delete/move/duplicate`,
  `arrange.group/ungroup/reorder`). Other mutating commands are refused in a shared session
  instead of silently diverging; the list is in `docs/collab/production.md`.
- Media covers pictures, audio and video; fonts and 3D models are still refused by the channel.
- The browser build has no `web-sys` link yet; the UI is honest about the offline state.
- The cabinet callback that turns `commit-result` into a new file version is a host-bridge
  contract and is not wired (same external blocker as WordCraft).
- Edits become visible on `applied`, not on the keystroke; optimistic preview is a later slice.
- Structural undo (slide/shape insert/delete) is out of v1; merge operations and, since
  `41fe1ad9`, fill/outline/`format.*` value steps of one shape are covered. A group's fill or
  outline step is not recorded (one object's image cannot put the members back).
- A client that missed a compacted journal tail cannot rebuild; a chunked base `snapshot` is the
  next step. Restart persistence is covered by the journal.

## Review guide

The stack is intentionally one commit per slice; review in this order:

| Branch | Slice |
|---|---|
| `collab/rfc` | RFC and ADRs 0001–0010 |
| `collab/pr1` | wire types, adapter, `apply_remote` |
| `collab/pr2` | per-user undo/redo |
| `collab/pr3` | `DocSession`: versions, dedup, snapshots, commit |
| `collab/pr4` | `ClientSession`: queue, dedup, resync, viewer |
| `collab/pr5` | commit/409, presence, two-client e2e |
| `collab/pr6` | UI behind a flag, presence, viewer gate |
| `collab/pr7` | `CollabDoc` glue, in-memory `Hub` |
| `collab/pr8` | WebSocket server, desktop link, UI wiring, undo requests, persistence |
| `collab/pr9` | text insert/delete with rebase, shape insert, engine command queue |
| `collab/pr10` | media channel: pictures by `sha256`, upload/fetch, persistence |

Only the final branch is meant to be pushed as `feature/realtime-collaboration`; the intermediate
branches exist for review.

## Known risks for reviewers

- The operation surface is small on purpose. Widening it needs a final-value normalisation per
  command; a raw `execute` on the wire would diverge on toggles and relative edits.
- The server is authoritative and stateful; horizontal scaling needs room-affinity, which is
  documented but not implemented.
- Media uploads are authenticated but content is not scanned; the allowlist is by MIME sniffing.
